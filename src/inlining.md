# การอินไลน์

การเข้าออกฟังก์ชันที่ฮอตและไม่ได้ถูกอินไลน์มักคิดเป็นสัดส่วนที่ไม่น้อยของเวลาทำงาน การอินไลน์ฟังก์ชันเหล่านี้ขจัดจุดเข้าและออกดังกล่าว และช่วยให้คอมไพเลอร์เพิ่มประสิทธิภาพระดับต่ำเพิ่มเติมได้ ในกรณีที่ดีที่สุด ผลโดยรวมคือความเร็วที่เพิ่มขึ้นเล็กน้อยแต่ได้มาง่ายๆ

มีแอตทริบิวต์อินไลน์ 4 แบบที่ใช้กับฟังก์ชัน Rust ได้
- **ไม่ระบุ**. คอมไพเลอร์จะตัดสินใจเองว่าฟังก์ชันควรถูกอินไลน์หรือไม่ โดยขึ้นอยู่กับปัจจัยต่างๆ เช่น ระดับการเพิ่มประสิทธิภาพ ขนาดของฟังก์ชัน ฟังก์ชันเป็นเจเนอริกหรือไม่ และการอินไลน์ข้ามเครตหรือไม่
- **`#[inline]`**. แนะนำว่าฟังก์ชันควรถูกอินไลน์
- **`#[inline(always)]`**. แนะนำอย่างยิ่งว่าฟังก์ชันควรถูกอินไลน์
- **`#[inline(never)]`**. แนะนำอย่างยิ่งว่าฟังก์ชันไม่ควรถูกอินไลน์

แอตทริบิวต์อินไลน์ไม่ได้การันตีว่าฟังก์ชันจะถูกอินไลน์หรือไม่ถูกอินไลน์ แต่ในทางปฏิบัติ `#[inline(always)]` จะทำให้เกิดการอินไลน์ในทุกกรณี ยกเว้นกรณีที่ผิดปกติที่สุด

การอินไลน์ไม่ถ่ายทอดกัน (non-transitive) หากฟังก์ชัน `f` เรียกฟังก์ชัน `g` และคุณต้องการให้ทั้งสองฟังก์ชันถูกอินไลน์รวมกันที่จุดเรียกใช้ `f` ทั้งสองฟังก์ชันควรถูกกำกับด้วยแอตทริบิวต์อินไลน์

## กรณีง่าย

ฟังก์ชันที่เหมาะแก่การอินไลน์ที่สุดคือ (ก) ฟังก์ชันที่เล็กมาก หรือ (ข) ฟังก์ชันที่มีจุดเรียกใช้เพียงจุดเดียว คอมไพเลอร์มักอินไลน์ฟังก์ชันเหล่านี้เองแม้ไม่มีแอตทริบิวต์อินไลน์ แต่คอมไพเลอร์ไม่สามารถเลือกสิ่งที่ดีที่สุดได้เสมอ บางครั้งจึงจำเป็นต้องใช้แอตทริบิวต์

Cachegrind เป็นโปรไฟเลอร์ที่ดีสำหรับตรวจสอบว่าฟังก์ชันถูกอินไลน์หรือไม่ เมื่อดูเอาต์พุตของ Cachegrind คุณจะรู้ได้ว่าฟังก์ชันถูกอินไลน์ก็ต่อเมื่อบรรทัดแรกและบรรทัดสุดท้ายของมัน *ไม่* ถูกกำกับด้วยจำนวนอีเวนต์ ตัวอย่างเช่น:
```text
      .  #[inline(always)]
      .  fn inlined(x: u32, y: u32) -> u32 {
700,000      eprintln!("inlined: {} + {}", x, y);
200,000      x + y
      .  }
      .  
      .  #[inline(never)]
400,000  fn not_inlined(x: u32, y: u32) -> u32 {
700,000      eprintln!("not_inlined: {} + {}", x, y);
200,000      x + y
200,000  }
```
คุณควรวัดผลอีกครั้งหลังจากเพิ่มแอตทริบิวต์อินไลน์ เพราะผลลัพธ์คาดเดาได้ยาก บางครั้งก็ไม่มีผลอะไรเลย เพราะฟังก์ชันใกล้เคียงที่เคยถูกอินไลน์กลับไม่ถูกอินไลน์อีกต่อไป บางครั้งก็ทำให้โค้ดช้าลง การอินไลน์ยังส่งผลต่อเวลาในการคอมไพล์ได้ด้วย โดยเฉพาะการอินไลน์ข้ามเครตซึ่งเกี่ยวข้องกับการทำสำเนาการแทนค่าภายในของฟังก์ชัน

## กรณีที่ยากขึ้น

บางครั้งคุณมีฟังก์ชันที่ใหญ่และมีจุดเรียกใช้หลายจุด แต่มีเพียงจุดเดียวที่ฮอต คุณต้องการอินไลน์จุดเรียกใช้ที่ฮอตเพื่อความเร็ว แต่ไม่อินไลน์จุดเรียกใช้ที่เย็นเพื่อหลีกเลี่ยงโค้ดบวมโดยไม่จำเป็น วิธีจัดการคือแยกฟังก์ชันออกเป็นเวอร์ชันที่อินไลน์เสมอและเวอร์ชันที่ไม่อินไลน์เลย โดยเวอร์ชันหลังเรียกเวอร์ชันแรก

ตัวอย่างเช่น ฟังก์ชันนี้:
```rust
# fn one() {};
# fn two() {};
# fn three() {};
fn my_function() {
    one();
    two();
    three();
}
```
จะกลายเป็นสองฟังก์ชันนี้:
```rust
# fn one() {};
# fn two() {};
# fn three() {};
// Use this at the hot call site.
#[inline(always)]
fn inlined_my_function() {
    one();
    two();
    three();
}

// Use this at the cold call sites.
#[inline(never)]
fn uninlined_my_function() {
    inlined_my_function();
}
```

## การเอาต์ไลน์

สิ่งที่ตรงข้ามกับการอินไลน์คือ *การเอาต์ไลน์ (outlining)*: การย้ายโค้ดที่แทบไม่ถูกเรียกไปไว้ในฟังก์ชันแยก คุณสามารถเพิ่มแอตทริบิวต์ `#[cold]` ให้ฟังก์ชันเหล่านั้นเพื่อบอกคอมไพเลอร์ว่าฟังก์ชันนี้แทบไม่ถูกเรียก ซึ่งอาจทำให้การสร้างโค้ดสำหรับพาธฮอตดีขึ้น

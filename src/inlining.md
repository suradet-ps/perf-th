# การอินไลน์

overhead ในการกระโดดเข้าและออกจากฟังก์ชันที่อยู่ใน hot path ซึ่งไม่ได้ถูกอินไลน์ (inlined) มักจะกินเวลาการทำงานไปไม่น้อย การอินไลน์ฟังก์ชันเหล่านี้จะช่วยกำจัดขั้นตอนการเรียกเข้าและออกจากฟังก์ชันดังกล่าวออกไป อีกทั้งยังช่วยเปิดทางให้คอมไพเลอร์ทำ low-level optimization เพิ่มเติมได้อีกด้วย ในกรณีที่ดีที่สุด ผลลัพธ์ที่ได้คือความเร็วที่เพิ่มขึ้นเล็กน้อยแต่ทำได้ง่าย

ในภาษา Rust มี attribute สำหรับควบคุมการอินไลน์ 4 รูปแบบที่สามารถนำมาใช้กับฟังก์ชันได้:
- **ไม่ระบุ** คอมไพเลอร์จะตัดสินใจเองว่าควรจะอินไลน์ฟังก์ชันนั้นหรือไม่ โดยพิจารณาจากปัจจัยต่างๆ เช่น ระดับการ optimize ขนาดของตัวฟังก์ชัน ฟังก์ชันนั้นเป็น generic หรือไม่ และเป็นการอินไลน์ข้าม crate หรือไม่
- **`#[inline]`** เป็นการแนะนำว่าฟังก์ชันนี้ควรได้รับการอินไลน์
- **`#[inline(always)]`** เป็นการแนะนำอย่างยิ่งว่าฟังก์ชันนี้ต้องได้รับการอินไลน์
- **`#[inline(never)]`** เป็นการแนะนำอย่างยิ่งว่าฟังก์ชันนี้ไม่ควรถูกอินไลน์

attribute สำหรับการอินไลน์เหล่านี้ไม่ได้การันตี 100% ว่าฟังก์ชันจะถูกอินไลน์หรือไม่ถูกอินไลน์เสมอไป แต่ในทางปฏิบัติ `#[inline(always)]` จะบังคับให้อินไลน์ได้เกือบทุกกรณียกเว้นสถานการณ์ที่ผิดปกติจริงๆ เท่านั้น

การอินไลน์ไม่มีผลถ่ายทอดต่อไปยังฟังก์ชันอื่น (non-transitive) หากฟังก์ชัน `f` เรียกฟังก์ชัน `g` และคุณต้องการให้ทั้งสองฟังก์ชันถูกอินไลน์รวมกันที่ตำแหน่งเรียกใช้งาน (call site) ของ `f` คุณจะต้องกำกับ attribute การอินไลน์ไว้ที่ฟังก์ชันทั้งสอง

## กรณีง่าย

ฟังก์ชันที่เหมาะแก่การอินไลน์มากที่สุดคือ (ก) ฟังก์ชันที่มีขนาดเล็กมาก หรือ (ข) ฟังก์ชันที่มีจุดเรียกใช้งาน (call site) เพียงจุดเดียวเท่านั้น บ่อยครั้งที่คอมไพเลอร์จะอินไลน์ฟังก์ชันเหล่านี้ให้เองโดยอัตโนมัติแม้จะไม่ได้ใส่ attribute ก็ตาม แต่คอมไพเลอร์ก็อาจไม่ได้ตัดสินใจเลือกสิ่งที่ดีที่สุดเสมอไป บางครั้งเราจึงจำเป็นต้องระบุ attribute ช่วย

Cachegrind เป็น profiler ที่ยอดเยี่ยมสำหรับการตรวจสอบว่าฟังก์ชันถูกอินไลน์หรือไม่ เมื่อดูเอาต์พุตของ Cachegrind คุณจะรู้ได้ว่าฟังก์ชันนั้นถูกอินไลน์ ก็ต่อเมื่อบรรทัดแรกและบรรทัดสุดท้ายของมัน *ไม่ได้* ถูกกำกับด้วยตัวเลขนับจำนวน event ตัวอย่างเช่น:
```text
      .  #[inline(always)]
      .  fn inlined(x: u32, y: u32) -> u32 {
700,000      eprintln!("inlined: {} + {}", x, y);
200,000      x + y
      .  }
      .  
      .  #[inline(never)]
400,000  fn not_inlined(x: u32, y: u32) -> u32 {
700,000      eprintln!("not_inlined: {} + {}", x, y);
200,000      x + y
200,000  }
```
คุณควรวัดผลซ้ำอีกครั้งหลังจากเพิ่ม attribute การอินไลน์เสมอ เนื่องจากผลลัพธ์อาจคาดเดาได้ยาก ในบางครั้งอาจไม่เห็นความเปลี่ยนแปลงเลย เพราะฟังก์ชันข้างเคียงที่เคยถูกอินไลน์กลับไม่ถูกอินไลน์อีกต่อไป และในบางกรณีก็อาจทำให้โค้ดทำงานช้าลงได้ นอกจากนี้ การอินไลน์ยังอาจส่งผลต่อเวลาในการคอมไพล์ โดยเฉพาะการอินไลน์ข้าม crate ซึ่งต้องมีการทำสำเนา representation ภายในของฟังก์ชันระหว่างคอมไพล์

## กรณีที่ยากขึ้น

บางครั้งคุณอาจมีฟังก์ชันขนาดใหญ่ที่มีจุดเรียกใช้งานอยู่หลายจุด แต่มีเพียงจุดเดียวเท่านั้นที่ทำงานบ่อย (hot call site) คุณย่อมต้องการอินไลน์เฉพาะจุดที่ทำงานบ่อยเพื่อเพิ่มความเร็ว แต่ไม่อยากให้อินไลน์จุดเรียกใช้งานอื่นๆ ที่ทำงานไม่บ่อย (cold call sites) เพื่อป้องกันไม่ให้โค้ดบวมโดยไม่จำเป็น วิธีจัดการกับกรณีนี้คือการแยกฟังก์ชันออกเป็นสองแบบ: แบบที่อินไลน์เสมอ กับแบบที่ไม่อินไลน์เลย โดยให้แบบหลังทำหน้าที่เรียกแบบแรก

ตัวอย่างเช่น ฟังก์ชันนี้:
```rust
# fn one() {};
# fn two() {};
# fn three() {};
fn my_function() {
    one();
    two();
    three();
}
```
จะกลายเป็นสองฟังก์ชันนี้:
```rust
# fn one() {};
# fn two() {};
# fn three() {};
// Use this at the hot call site.
#[inline(always)]
fn inlined_my_function() {
    one();
    two();
    three();
}

// Use this at the cold call sites.
#[inline(never)]
fn uninlined_my_function() {
    inlined_my_function();
}
```

## การเอาต์ไลน์

ทิศทางตรงกันข้ามกับการอินไลน์ก็คือ *การเอาต์ไลน์ (outlining)* ซึ่งเป็นการย้ายโค้ดส่วนที่แทบไม่เคยถูกรันออกไปไว้ในฟังก์ชันแยกต่างหาก คุณสามารถใส่ attribute `#[cold]` ให้กับฟังก์ชันเหล่านั้นเพื่อบอกคอมไพเลอร์ว่าฟังก์ชันนี้แทบไม่ถูกเรียกใช้งาน ซึ่งจะช่วยให้คอมไพเลอร์สามารถสร้าง machine code สำหรับ hot path ได้มีประสิทธิภาพดียิ่งขึ้น

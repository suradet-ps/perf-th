# การแฮช

`HashSet` และ `HashMap` เป็นชนิดข้อมูลที่ถูกใช้อย่างแพร่หลายสองชนิด และมีวิธีทำให้มันเร็วขึ้นได้

## ตัวแฮชทางเลือก

อัลกอริทึมการแฮชเริ่มต้นไม่ได้ถูกระบุไว้ตายตัว แต่ ณ เวลาที่เขียนหนังสือเล่มนี้ ค่าเริ่มต้นคืออัลกอริทึมชื่อ [SipHash 1-3] อัลกอริทึมนี้มีคุณภาพสูง—ให้การป้องกันการชนกัน (collision) ในระดับสูง—แต่ค่อนข้างช้า โดยเฉพาะกับคีย์สั้นๆ เช่นจำนวนเต็ม

[SipHash 1-3]: https://en.wikipedia.org/wiki/SipHash

หากการโปรไฟล์แสดงว่าการแฮชเป็นจุดฮอต และ[การโจมตี HashDoS]ไม่ใช่ข้อกังวลสำหรับแอปพลิเคชันของคุณ การใช้ตารางแฮชกับอัลกอริทึมการแฮชที่เร็วกว่าสามารถให้ความเร็วที่เพิ่มขึ้นอย่างมาก
- [`rustc-hash`] มีชนิดข้อมูล `FxHashSet` และ `FxHashMap` ที่ใช้แทน `HashSet` และ `HashMap` ได้ทันที (drop-in replacement) อัลกอริทึมการแฮชของมันมีคุณภาพต่ำแต่เร็วมาก โดยเฉพาะกับคีย์ที่เป็นจำนวนเต็ม และพบว่าทำงานได้ดีกว่าอัลกอริทึมการแฮชอื่นทั้งหมดภายใน rustc ([`fxhash`] เป็นอิมพลีเมนเทชันที่เก่ากว่าและดูแลรักษาน้อยกว่าของอัลกอริทึมและชนิดข้อมูลเดียวกัน)
- [`fnv`] มีชนิดข้อมูล `FnvHashSet` และ `FnvHashMap` อัลกอริทึมการแฮชของมันมีคุณภาพสูงกว่า `rustc-hash` แต่ช้ากว่าเล็กน้อย
- [`ahash`] มี `AHashSet` และ `AHashMap` อัลกอริทึมการแฮชของมันสามารถใช้ประโยชน์จากการรองรับคำสั่ง AES ที่มีอยู่ในโปรเซสเซอร์บางรุ่นได้

[การโจมตี HashDoS]: https://en.wikipedia.org/wiki/Collision_attack
[`rustc-hash`]: https://crates.io/crates/rustc-hash
[`fxhash`]: https://crates.io/crates/fxhash
[`fnv`]: https://crates.io/crates/fnv
[`ahash`]: https://crates.io/crates/ahash

หากประสิทธิภาพการแฮชมีความสำคัญในโปรแกรมของคุณ การลองมากกว่าหนึ่งทางเลือกนั้นคุ้มค่า ตัวอย่างเช่น ผลลัพธ์ต่อไปนี้พบใน rustc
- การเปลี่ยนจาก `fnv` เป็น `fxhash` ให้[ความเร็วเพิ่มขึ้นถึง 6%][fnv2fx]
- ความพยายามเปลี่ยนจาก `fxhash` เป็น `ahash` กลับทำให้[ช้าลง 1-4%][fx2a]
- ความพยายามเปลี่ยนจาก `fxhash` กลับไปใช้ตัวแฮชเริ่มต้นกลับทำให้[ช้าลงตั้งแต่ 4-84%][fx2default]!

[fnv2fx]: https://github.com/rust-lang/rust/pull/37229/commits/00e48affde2d349e3b3bfbd3d0f6afb5d76282a7
[fx2a]: https://github.com/rust-lang/rust/issues/69153#issuecomment-589504301
[fx2default]: https://github.com/rust-lang/rust/issues/69153#issuecomment-589338446

หากคุณตัดสินใจใช้ทางเลือกใดทางเลือกหนึ่งโดยทั่วทั้งโปรเจกต์ เช่น `FxHashSet`/`FxHashMap` ก็เป็นเรื่องง่ายที่จะเผลอใช้ `HashSet`/`HashMap` ในบางจุด คุณสามารถ[ใช้ Clippy]เพื่อหลีกเลี่ยงปัญหานี้ได้

[ใช้ Clippy]: linting.md#การหามใชชนดขอมล

บางชนิดข้อมูลไม่จำเป็นต้องแฮช ตัวอย่างเช่น คุณอาจมีนิวไทป์ที่ห่อจำนวนเต็มไว้ และค่าจำนวนเต็มนั้นเป็นค่าสุ่มหรือใกล้เคียงค่าสุ่ม สำหรับชนิดข้อมูลเช่นนี้ การแจกแจงของค่าแฮชจะไม่ต่างจากการแจกแจงของค่าตัวมันเองมากนัก ในกรณีนี้เครต [`nohash_hasher`] มีประโยชน์ได้

[`nohash_hasher`]: https://crates.io/crates/nohash-hasher

การออกแบบฟังก์ชันแฮชเป็นหัวข้อที่ซับซ้อนและอยู่นอกขอบเขตของหนังสือเล่มนี้ [เอกสารของ `ahash`] มีการอธิบายที่ดี

[เอกสารของ `ahash`]: https://github.com/tkaitchuck/aHash/blob/master/compare/readme.md

## การแฮชแบบรายไบต์

เมื่อคุณกำกับชนิดข้อมูลด้วย `#[derive(Hash)]` เมธอด `hash` ที่ถูกสร้างขึ้นจะแฮชแต่ละฟิลด์แยกกัน สำหรับฟังก์ชันแฮชบางตัว การแปลงชนิดข้อมูลเป็นไบต์ดิบแล้วแฮชไบต์เป็นสตรีมอาจเร็วกว่า ซึ่งเป็นไปได้สำหรับชนิดข้อมูลที่มีคุณสมบัติบางประการ เช่น ไม่มีไบต์แพดดิง

เครต [`zerocopy`] และ [`bytemuck`] ต่างก็มีมาโคร `#[derive(ByteHash)]` ที่สร้างเมธอด `hash` ซึ่งทำการแฮชแบบรายไบต์ลักษณะนี้ README ของเครต [`derive_hash_fast`] อธิบายเทคนิคนี้ไว้ละเอียดกว่า

[`zerocopy`]: https://crates.io/crates/zerocopy
[`bytemuck`]: https://crates.io/crates/bytemuck
[`derive_hash_fast`]: https://crates.io/crates/derive_hash_fast

นี่เป็นเทคนิคขั้นสูง และผลต่อประสิทธิภาพขึ้นอยู่กับฟังก์ชันแฮชและโครงสร้างที่แน่นอนของชนิดข้อมูลที่ถูกแฮชอย่างมาก ควรวัดผลอย่างระมัดระวัง

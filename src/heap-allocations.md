# การจัดสรรหน่วยความจำบนฮีป

การจัดสรรหน่วยความจำบนฮีป (heap allocation) มีต้นทุนปานกลาง รายละเอียดที่แน่นอนขึ้นอยู่กับอัลโลเคเตอร์ที่ใช้งานอยู่ แต่การจัดสรร (และการคืนหน่วยความจำ) แต่ละครั้งมักเกี่ยวข้องกับการจับล็อกส่วนกลาง การจัดการโครงสร้างข้อมูลที่ไม่ธรรมดาบางอย่าง และอาจเรียกใช้ระบบปฏิบัติการด้วย การจัดสรรขนาดเล็กไม่ได้ถูกกว่าการจัดสรรขนาดใหญ่เสมอไป การเข้าใจว่าโครงสร้างข้อมูลและการดำเนินการใดของ Rust ที่ทำให้เกิดการจัดสรรนั้นคุ้มค่า เพราะการหลีกเลี่ยงมันสามารถปรับปรุงประสิทธิภาพได้อย่างมาก

[Rust Container Cheat Sheet] มีภาพประกอบของชนิดข้อมูล Rust ที่ใช้บ่อย และเป็นเพื่อนคู่หูที่ยอดเยี่ยมสำหรับหัวข้อต่อไปนี้

[Rust Container Cheat Sheet]: https://docs.google.com/presentation/d/1q-c7UAyrUlM-eZyTo1pd8SZ0qwA_wYxmPZVOQkoDmH4/

## การโปรไฟล์

หากโปรไฟเลอร์เอนกประสงค์รายงานว่า `malloc`, `free` และฟังก์ชันที่เกี่ยวข้องเป็นจุดฮอต ก็มักคุ้มค่าที่จะลองลดอัตราการจัดสรร และ/หรือใช้อัลโลเคเตอร์ทางเลือก

[DHAT] เป็นโปรไฟเลอร์ที่ยอดเยี่ยมสำหรับใช้เมื่อต้องการลดอัตราการจัดสรร ทำงานบน Linux และยูนิกซ์อื่นๆ บางระบบ โดยระบุจุดที่มีการจัดสรรสูงและอัตราการจัดสรรได้อย่างแม่นยำ ผลลัพธ์ที่แน่นอนจะแตกต่างกันไป แต่ประสบการณ์กับ rustc แสดงให้เห็นว่าการลดอัตราการจัดสรรลง 10 ครั้งต่อการเรียกใช้หนึ่งล้านคำสั่งสามารถสร้างการปรับปรุงประสิทธิภาพที่วัดได้ (เช่น ประมาณ 1%)

[DHAT]: https://www.valgrind.org/docs/manual/dh-manual.html

## `Box`

[`Box`] เป็นชนิดข้อมูลที่จัดสรรบนฮีปอย่างง่ายที่สุด ค่า `Box<T>` คือค่า `T` ที่ถูกจัดสรรบนฮีป

[`Box`]: https://doc.rust-lang.org/std/boxed/struct.Box.html

บางครั้งการใส่ `Box` ให้กับฟิลด์หนึ่งหรือหลายฟิลด์ใน struct หรือฟิลด์ของ enum ก็คุ้มค่า เพื่อทำให้ชนิดข้อมูลเล็กลง (ดูบท[ขนาดชนิดข้อมูล](type-sizes.md) สำหรับรายละเอียดเพิ่มเติมเกี่ยวกับเรื่องนี้)

นอกจากนั้น `Box` ก็ตรงไปตรงมาและไม่ได้เปิดช่องให้เพิ่มประสิทธิภาพได้มากนัก

## `Rc`/`Arc`

[`Rc`]/[`Arc`] คล้ายกับ `Box` แต่ค่าบนฮีปจะมาพร้อมกับตัวนับการอ้างอิง (reference count) สองตัว ช่วยให้แชร์ค่าได้ ซึ่งอาจเป็นวิธีที่มีประสิทธิผลในการลดการใช้หน่วยความจำ

[`Rc`]: https://doc.rust-lang.org/std/rc/struct.Rc.html
[`Arc`]: https://doc.rust-lang.org/std/sync/struct.Arc.html

อย่างไรก็ตาม หากใช้กับค่าที่ไม่ค่อยถูกแชร์ มันอาจเพิ่มอัตราการจัดสรรได้ เพราะจัดสรรค่าบนฮีปที่ปกติอาจไม่ต้องจัดสรรบนฮีป
[**ตัวอย่าง**](https://github.com/rust-lang/rust/pull/37373/commits/c440a7ae654fb641e68a9ee53b03bf3f7133c2fe).

ต่างจาก `Box` การเรียก `clone` บนค่า `Rc`/`Arc` ไม่เกี่ยวข้องกับการจัดสรร แต่เพียงเพิ่มตัวนับการอ้างอิงเท่านั้น

## `Vec`

[`Vec`] เป็นชนิดข้อมูลที่จัดสรรบนฮีป ซึ่งมีช่องให้เพิ่มประสิทธิภาพได้มากมาย ทั้งการลดจำนวนครั้งในการจัดสรร และ/หรือลดพื้นที่ที่สูญเปล่าให้เหลือน้อยที่สุด การทำเช่นนี้ต้องเข้าใจว่าองค์ประกอบของมันถูกจัดเก็บอย่างไร

[`Vec`]: https://doc.rust-lang.org/std/vec/struct.Vec.html

`Vec` ประกอบด้วยสามคำ (word) ได้แก่ ความยาว (length) ความจุ (capacity) และพอยเตอร์ (pointer) พอยเตอร์จะชี้ไปยังหน่วยความจำที่จัดสรรบนฮีป หากความจุไม่เป็นศูนย์และขนาดขององค์ประกอบไม่เป็นศูนย์ มิฉะนั้นจะไม่ชี้ไปยังหน่วยความจำที่จัดสรรไว้

แม้ว่า `Vec` เองจะไม่ได้ถูกจัดสรรบนฮีป องค์ประกอบของมัน (หากมีและมีขนาดไม่เป็นศูนย์) ก็จะถูกจัดสรรบนฮีปเสมอ หากมีองค์ประกอบที่มีขนาดไม่เป็นศูนย์อยู่ หน่วยความจำที่เก็บองค์ประกอบเหล่านั้นอาจใหญ่เกินความจำเป็น เพื่อเผื่อพื้นที่สำหรับองค์ประกอบเพิ่มเติมในอนาคต จำนวนองค์ประกอบที่มีอยู่คือความยาว และจำนวนองค์ประกอบที่เก็บได้โดยไม่ต้องจัดสรรใหม่คือความจุ

เมื่อเวกเตอร์ต้องขยายเกินความจุปัจจุบัน องค์ประกอบจะถูกคัดลอกไปยังหน่วยความจำฮีปที่ใหญ่ขึ้น และหน่วยความจำฮีปเดิมจะถูกคืน

### การเติบโตของ `Vec`

`Vec` ใหม่ที่ว่างเปล่า ซึ่งสร้างด้วยวิธีทั่วไป ([`vec![]`](https://doc.rust-lang.org/std/macro.vec.html) หรือ [`Vec::new`] หรือ [`Vec::default`]) มีความยาวและความจุเป็นศูนย์ และไม่ต้องจัดสรรหน่วยความจำบนฮีป หากคุณพุชองค์ประกอบทีละตัวต่อท้าย `Vec` ซ้ำๆ มันจะจัดสรรใหม่เป็นระยะ กลยุทธ์การเติบโตไม่ได้ถูกกำหนดไว้ตายตัว แต่ ณ เวลาที่เขียนหนังสือเล่มนี้ มันใช้กลยุทธ์แบบเกือบเพิ่มเป็นสองเท่า ซึ่งให้ความจุดังนี้: 0, 4, 8, 16, 32, 64 และต่อไปเรื่อยๆ (มันข้ามจาก 0 ไปเป็น 4 โดยตรง แทนที่จะผ่าน 1 และ 2 เพราะในทางปฏิบัติวิธีนี้[หลีกเลี่ยงการจัดสรรหลายครั้ง]) เมื่อเวกเตอร์เติบโตขึ้น ความถี่ในการจัดสรรใหม่จะลดลงแบบเอกซ์โพเนนเชียล แต่ปริมาณความจุส่วนเกินที่อาจสูญเปล่าจะเพิ่มขึ้นแบบเอกซ์โพเนนเชียล

[`Vec::new`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.new
[`Vec::default`]: https://doc.rust-lang.org/std/default/trait.Default.html#tymethod.default
[หลีกเลี่ยงการจัดสรรหลายครั้ง]: https://github.com/rust-lang/rust/pull/72227

กลยุทธ์การเติบโตนี้เป็นเรื่องปกติสำหรับโครงสร้างข้อมูลที่ขยายได้ และสมเหตุสมผลในกรณีทั่วไป แต่ถ้าคุณทราบล่วงหน้าถึงความยาวที่เป็นไปได้ของเวกเตอร์ คุณมักทำได้ดีกว่านั้น หากคุณมีจุดจัดสรรเวกเตอร์ที่ฮอต (เช่น การเรียก [`Vec::push`] ที่ฮอต) การใช้ [`eprintln!`] พิมพ์ความยาวของเวกเตอร์ที่จุดนั้น แล้วประมวลผลภายหลัง (เช่น ด้วย [`counts`]) เพื่อหาการกระจายตัวของความยาวก็คุ้มค่า ตัวอย่างเช่น คุณอาจมีเวกเตอร์สั้นๆ จำนวนมาก หรือมีเวกเตอร์ยาวมากจำนวนน้อยกว่า และวิธีที่ดีที่สุดในการเพิ่มประสิทธิภาพจุดจัดสรรนั้นจะแตกต่างกันไปตามกรณี

[`Vec::push`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.push
[`eprintln!`]: https://doc.rust-lang.org/std/macro.eprintln.html
[`counts`]: https://github.com/nnethercote/counts/

### `Vec` ขนาดสั้น

หากคุณมีเวกเตอร์สั้นๆ จำนวนมาก คุณสามารถใช้ชนิดข้อมูล `SmallVec` จากเครต [`smallvec`] ได้ `SmallVec<[T; N]>` เป็นตัวแทนที่ใช้แทน `Vec` ได้ทันที (drop-in replacement) ซึ่งเก็บองค์ประกอบได้ `N` ตัวไว้ภายใน `SmallVec` เอง แล้วจึงเปลี่ยนไปจัดสรรบนฮีปหากจำนวนองค์ประกอบเกินกว่านั้น (โปรดทราบด้วยว่าลิเทอรัล `vec![]` ต้องถูกแทนที่ด้วยลิเทอรัล `smallvec![]`)
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/50565/commits/78262e700dc6a7b57e376742f344e80115d2d3f2),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/55383/commits/526dc1421b48e3ee8357d58d997e7a0f4bb26915).

[`smallvec`]: https://crates.io/crates/smallvec

`SmallVec` ลดอัตราการจัดสรรได้อย่างน่าเชื่อถือเมื่อใช้อย่างเหมาะสม แต่การใช้มันไม่ได้การันตีว่าประสิทธิภาพจะดีขึ้น มันช้ากว่า `Vec` เล็กน้อยสำหรับการดำเนินการทั่วไป เพราะต้องตรวจสอบเสมอว่าองค์ประกอบถูกจัดสรรบนฮีปหรือไม่ นอกจากนี้ หาก `N` สูงหรือ `T` มีขนาดใหญ่ `SmallVec<[T; N]>` เองอาจใหญ่กว่า `Vec<T>` และการคัดลอกค่า `SmallVec` จะช้ากว่า เช่นเคย จำเป็นต้องทำเบนช์มาร์กเพื่อยืนยันว่าการเพิ่มประสิทธิภาพนั้นได้ผลจริง

หากคุณมีเวกเตอร์สั้นๆ จำนวนมาก *และ* ทราบความยาวสูงสุดของมันอย่างแม่นยำ `ArrayVec` จากเครต [`arrayvec`] เป็นทางเลือกที่ดีกว่า `SmallVec` เพราะไม่ต้องเปลี่ยนไปจัดสรรบนฮีปสำรอง ซึ่งทำให้เร็วขึ้นเล็กน้อย
[**ตัวอย่าง**](https://github.com/rust-lang/rust/pull/74310/commits/c492ca40a288d8a85353ba112c4d38fe87ef453e).

[`arrayvec`]: https://crates.io/crates/arrayvec

### `Vec` ขนาดยาว

หากคุณทราบขนาดขั้นต่ำหรือขนาดที่แน่นอนของเวกเตอร์ คุณสามารถจองความจุที่เจาะจงได้ด้วย [`Vec::with_capacity`], [`Vec::reserve`] หรือ [`Vec::reserve_exact`] ตัวอย่างเช่น หากคุณทราบว่าเวกเตอร์จะเติบโตจนมีองค์ประกอบอย่างน้อย 20 ตัว ฟังก์ชันเหล่านี้สามารถให้เวกเตอร์ที่มีความจุอย่างน้อย 20 ได้ทันทีด้วยการจัดสรรเพียงครั้งเดียว ในขณะที่การพุชทีละตัวจะทำให้เกิดการจัดสรรสี่ครั้ง (สำหรับความจุ 4, 8, 16 และ 32)
[**ตัวอย่าง**](https://github.com/rust-lang/rust/pull/77990/commits/a7f2bb634308a5f05f2af716482b67ba43701681).

[`Vec::with_capacity`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.with_capacity
[`Vec::reserve`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.reserve
[`Vec::reserve_exact`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.reserve_exact

หากคุณทราบความยาวสูงสุดของเวกเตอร์ ฟังก์ชันข้างต้นยังช่วยให้คุณไม่ต้องจัดสรรพื้นที่ส่วนเกินโดยไม่จำเป็นอีกด้วย ในทำนองเดียวกัน [`Vec::shrink_to_fit`] สามารถใช้ลดพื้นที่ที่สูญเปล่าให้เหลือน้อยที่สุดได้ แต่โปรดทราบว่ามันอาจทำให้เกิดการจัดสรรใหม่

[`Vec::shrink_to_fit`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.shrink_to_fit

## `String`

[`String`] เก็บไบต์ที่จัดสรรบนฮีป การแทนค่าและการทำงานของ `String` นั้นคล้ายกับ `Vec<u8>` มาก เมธอดของ `Vec` หลายตัวที่เกี่ยวกับการเติบโตและความจุมีเมธอดเทียบเท่าสำหรับ `String` เช่น [`String::with_capacity`]

[`String`]: https://doc.rust-lang.org/std/string/struct.String.html
[`String::with_capacity`]: https://doc.rust-lang.org/std/string/struct.String.html#method.with_capacity

ชนิดข้อมูล `SmallString` จากเครต [`smallstr`] คล้ายกับชนิดข้อมูล `SmallVec`

[`smallstr`]: https://crates.io/crates/smallstr

ชนิดข้อมูล `String` จากเครต [`smartstring`] เป็นตัวแทนที่ใช้แทน `String` ได้ทันที ซึ่งหลีกเลี่ยงการจัดสรรบนฮีปสำหรับสตริงที่มีอักขระน้อยกว่าพื้นที่สามคำ บนแพลตฟอร์ม 64 บิต นั่นหมายถึงสตริงใดก็ตามที่มีขนาดน้อยกว่า 24 ไบต์ ซึ่งรวมถึงสตริงทั้งหมดที่มีอักขระ ASCII 23 ตัวหรือน้อยกว่า

[`smartstring`]: https://crates.io/crates/smartstring

## `clone`

การเรียก [`clone`] บนค่าที่มีหน่วยความจำจัดสรรบนฮีปอยู่ภายใน มักเกี่ยวข้องกับการจัดสรรเพิ่มเติม ตัวอย่างเช่น การเรียก `clone` บน `Vec` ที่ไม่ว่างเปล่าต้องมีการจัดสรรใหม่สำหรับองค์ประกอบ (แต่โปรดทราบว่าความจุของ `Vec` ใหม่ อาจไม่เท่ากับความจุของ `Vec` เดิม) ข้อยกเว้นคือ `Rc`/`Arc` ซึ่งการเรียก `clone` เพียงเพิ่มตัวนับการอ้างอิงเท่านั้น

[`clone`]: https://doc.rust-lang.org/std/clone/trait.Clone.html#tymethod.clone

[`clone_from`] เป็นทางเลือกแทน `clone` โดย `a.clone_from(&b)` เทียบเท่ากับ `a = b.clone()` แต่ช่วยหลีกเลี่ยงการจัดสรรที่ไม่จำเป็นได้ ตัวอย่างเช่น หากคุณต้องการโคลน `Vec` หนึ่งทับลงบน `Vec` ที่มีอยู่ หน่วยความจำฮีปของ `Vec` เดิมจะถูกนำกลับมาใช้ใหม่หากเป็นไปได้ ดังที่ตัวอย่างต่อไปนี้แสดง
```rust
let mut v1: Vec<u32> = Vec::with_capacity(99);
let v2: Vec<u32> = vec![1, 2, 3];
v1.clone_from(&v2); // v1's allocation is reused
assert_eq!(v1.capacity(), 99);
```
แม้ว่า `clone` มักทำให้เกิดการจัดสรร แต่ก็เป็นสิ่งที่สมเหตุสมผลที่จะใช้ในหลายสถานการณ์ และมักทำให้โค้ดเรียบง่ายขึ้น ใช้ข้อมูลการโปรไฟล์เพื่อดูว่าการเรียก `clone` จุดใดที่ฮอตและคุ้มค่าที่จะใช้ความพยายามหลีกเลี่ยง

[`clone_from`]: https://doc.rust-lang.org/std/clone/trait.Clone.html#method.clone_from

บางครั้งโค้ด Rust ก็มีการเรียก `clone` ที่ไม่จำเป็นหลงเหลืออยู่ เนื่องจาก (ก) ความผิดพลาดของโปรแกรมเมอร์ หรือ (ข) การเปลี่ยนแปลงในโค้ดที่ทำให้การเรียก `clone` ซึ่งเคยจำเป็นกลายเป็นไม่จำเป็น หากคุณเห็นการเรียก `clone` ที่ฮอตซึ่งดูเหมือนไม่จำเป็น บางครั้งมันก็อาจถูกลบออกได้เลย

[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/37318/commits/e382267cfb9133ef12d59b66a2935ee45b546a61),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/37705/commits/11c1126688bab32f76dbe1a973906c7586da143f),
[**ตัวอย่างที่ 3**](https://github.com/rust-lang/rust/pull/64302/commits/36b37e22de92b584b9cf4464ed1d4ad317b798be).

## `to_owned`

[`ToOwned::to_owned`] ถูกอิมพลีเมนต์สำหรับชนิดข้อมูลทั่วไปหลายชนิด มันสร้างข้อมูลแบบเป็นเจ้าของจากข้อมูลแบบยืม จึงมักทำให้เกิดการจัดสรรบนฮีป ตัวอย่างเช่น มันใช้สร้าง `String` จาก `&str` ได้

[`ToOwned::to_owned`]: https://doc.rust-lang.org/std/borrow/trait.ToOwned.html#tymethod.to_owned

บางครั้งการเรียก `to_owned` (และการเรียกที่เกี่ยวข้อง เช่น `clone` และ `to_string`) สามารถหลีกเลี่ยงได้โดยเก็บการอ้างอิงไปยังข้อมูลแบบยืมไว้ใน struct แทนที่จะเก็บสำเนาแบบเป็นเจ้าของ วิธีนี้ต้องมีคำกำกับไลฟ์ไทม์ (lifetime annotation) บน struct ซึ่งทำให้โค้ดซับซ้อนขึ้น และควรทำเฉพาะเมื่อการโปรไฟล์และการทำเบนช์มาร์กแสดงว่าคุ้มค่าเท่านั้น
[**ตัวอย่าง**](https://github.com/rust-lang/rust/pull/50855/commits/6872377357dbbf373cfd2aae352cb74cfcc66f34).

## `Cow`

บางครั้งโค้ดต้องจัดการกับข้อมูลผสมระหว่างแบบยืมและแบบเป็นเจ้าของ ลองนึกภาพเวกเตอร์ของข้อความแสดงข้อผิดพลาด ซึ่งบางส่วนเป็นสตริงลิเทอรัลแบบสแตติกและบางส่วนสร้างด้วย `format!` การแทนค่าที่ชัดเจนคือ `Vec<String>` ดังที่ตัวอย่างต่อไปนี้แสดง
```rust
let mut errors: Vec<String> = vec![];
errors.push("something went wrong".to_string());
errors.push(format!("something went wrong on line {}", 100));
```
วิธีนี้ต้องเรียก `to_string` เพื่อยกระดับสตริงลิเทอรัลแบบสแตติกให้เป็น `String` ซึ่งก่อให้เกิดการจัดสรร

แต่คุณสามารถใช้ชนิดข้อมูล [`Cow`] แทนได้ ซึ่งเก็บได้ทั้งข้อมูลแบบยืมและแบบเป็นเจ้าของ ค่าแบบยืม `x` จะถูกห่อด้วย `Cow::Borrowed(x)` และค่าแบบเป็นเจ้าของ `y` จะถูกห่อด้วย `Cow::Owned(y)` นอกจากนี้ `Cow` ยังอิมพลีเมนต์เทรต `From<T>` สำหรับชนิดสตริง สไลซ์ และพาธต่างๆ ดังนั้นคุณมักใช้ `into` ได้เช่นกัน (หรือ `Cow::from` ซึ่งยาวกว่าแต่ทำให้โค้ดอ่านง่ายกว่า เพราะระบุชนิดข้อมูลได้ชัดเจนขึ้น) ตัวอย่างต่อไปนี้รวมทุกอย่างเข้าด้วยกัน

[`Cow`]: https://doc.rust-lang.org/std/borrow/enum.Cow.html

```rust
use std::borrow::Cow;
let mut errors: Vec<Cow<'static, str>> = vec![];
errors.push(Cow::Borrowed("something went wrong"));
errors.push(Cow::Owned(format!("something went wrong on line {}", 100)));
errors.push(Cow::from("something else went wrong"));
errors.push(format!("something else went wrong on line {}", 101).into());
```
ตอนนี้ `errors` เก็บข้อมูลผสมระหว่างแบบยืมและแบบเป็นเจ้าของโดยไม่ต้องจัดสรรเพิ่มเติมใดๆ ตัวอย่างนี้ใช้ `&str`/`String` แต่คู่อื่นๆ เช่น `&[T]`/`Vec<T>` และ `&Path`/`PathBuf` ก็เป็นไปได้เช่นกัน

[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/37064/commits/b043e11de2eb2c60f7bfec5e15960f537b229e20),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/56336/commits/787959c20d062d396b97a5566e0a766d963af022).

ทั้งหมดที่กล่าวมาข้างต้นใช้ได้เมื่อข้อมูลไม่ถูกแก้ไข แต่ `Cow` ยังอนุญาตให้ยกระดับข้อมูลแบบยืมเป็นข้อมูลแบบเป็นเจ้าของได้หากจำเป็นต้องแก้ไข [`Cow::to_mut`] จะขอการอ้างอิงแบบเปลี่ยนได้ไปยังค่าแบบเป็นเจ้าของ โดยโคลนหากจำเป็น พฤติกรรมนี้เรียกว่า "clone-on-write" ซึ่งเป็นที่มาของชื่อ `Cow`

[`Deref`]: https://doc.rust-lang.org/std/ops/trait.Deref.html
[`Cow::to_mut`]: https://doc.rust-lang.org/std/borrow/enum.Cow.html#method.to_mut

พฤติกรรม clone-on-write นี้มีประโยชน์เมื่อคุณมีข้อมูลแบบยืม เช่น `&str` ที่ส่วนใหญ่อ่านอย่างเดียวแต่บางครั้งต้องแก้ไข

[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/50855/commits/ad471452ba6fbbf91ad566dc4bdf1033a7281811),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/68848/commits/67da45f5084f98eeb20cc6022d68788510dc832a).

สุดท้าย เพราะ `Cow` อิมพลีเมนต์ [`Deref`] คุณจึงเรียกเมธอดบนข้อมูลที่มันห่อหุ้มได้โดยตรง

`Cow` อาจจุกจิกในการทำให้ใช้งานได้ แต่ก็มักคุ้มค่ากับความพยายาม

## การนำคอลเลกชันกลับมาใช้ซ้ำ

บางครั้งคุณต้องสร้างคอลเลกชันอย่าง `Vec` ขึ้นมาเป็นขั้นตอน โดยปกติแล้วการทำเช่นนี้โดยแก้ไข `Vec` ตัวเดียวจะดีกว่าการสร้าง `Vec` หลายตัวแล้วนำมารวมกันในภายหลัง

ตัวอย่างเช่น หากคุณมีฟังก์ชัน `do_stuff` ที่สร้าง `Vec` ออกมาและอาจถูกเรียกหลายครั้ง:
```rust
fn do_stuff(x: u32, y: u32) -> Vec<u32> {
    vec![x, y]
}
```
การแก้ไข `Vec` ที่ส่งเข้ามาแทนอาจดีกว่า:
```rust
fn do_stuff(x: u32, y: u32, vec: &mut Vec<u32>) {
    vec.push(x);
    vec.push(y);
}
```
บางครั้งการเก็บคอลเลกชัน "ตัวทำงานหลัก" (workhorse) ไว้ใช้ซ้ำก็คุ้มค่า ตัวอย่างเช่น หากต้องใช้ `Vec` ในแต่ละรอบของลูป คุณอาจประกาศ `Vec` ไว้นอกลูป ใช้มันภายในเนื้อลูป แล้วเรียก [`clear`] ที่ท้ายเนื้อลูป (เพื่อล้าง `Vec` โดยไม่กระทบความจุของมัน) วิธีนี้หลีกเลี่ยงการจัดสรรได้ แลกกับการทำให้เห็นไม่ชัดเจนว่าการใช้ `Vec` ในแต่ละรอบไม่เกี่ยวข้องกัน
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/77990/commits/45faeb43aecdc98c9e3f2b24edf2ecc71f39d323),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/51870/commits/b0c78120e3ecae5f4043781f7a3f79e2277293e7).

[`clear`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.clear

ในทำนองเดียวกัน บางครั้งการเก็บคอลเลกชันตัวทำงานหลักไว้ใน struct เพื่อใช้ซ้ำในเมธอดหนึ่งหรือหลายเมธอดที่ถูกเรียกซ้ำๆ ก็คุ้มค่า

## การอ่านไฟล์ทีละบรรทัด

[`BufRead::lines`] ทำให้การอ่านไฟล์ทีละบรรทัดเป็นเรื่องง่าย:
```rust
# fn blah() -> Result<(), std::io::Error> {
# fn process(_: &str) {}
use std::io::{self, BufRead};
let mut lock = io::stdin().lock();
for line in lock.lines() {
    process(&line?);
}
# Ok(())
# }
```
แต่อิเทอเรเตอร์ที่มันสร้างขึ้นคืนค่า `io::Result<String>` ซึ่งหมายความว่ามันจัดสรรหน่วยความจำใหม่ทุกบรรทัดในไฟล์

[`BufRead::lines`]: https://doc.rust-lang.org/stable/std/io/trait.BufRead.html#method.lines

ทางเลือกหนึ่งคือใช้ `String` ตัวทำงานหลักในลูปที่วนเรียก
[`BufRead::read_line`]:
```rust
# fn blah() -> Result<(), std::io::Error> {
# fn process(_: &str) {}
use std::io::{self, BufRead};
let mut lock = io::stdin().lock();
let mut line = String::new();
while lock.read_line(&mut line)? != 0 {
    process(&line);
    line.clear();
}
# Ok(())
# }
```
วิธีนี้ลดจำนวนครั้งในการจัดสรรลงเหลือไม่เกินหยิบมือ และอาจเหลือเพียงครั้งเดียว (จำนวนที่แน่นอนขึ้นอยู่กับว่าต้องจัดสรร `line` ใหม่กี่ครั้ง ซึ่งขึ้นอยู่กับการกระจายตัวของความยาวบรรทัดในไฟล์)

วิธีนี้จะใช้ได้เฉพาะเมื่อเนื้อลูปทำงานกับ `&str` ได้ ไม่ใช่ `String`

[`BufRead::read_line`]: https://doc.rust-lang.org/stable/std/io/trait.BufRead.html#method.read_line

[**ตัวอย่าง**](https://github.com/nnethercote/counts/commit/7d39bbb1867720ef3b9799fee739cd717ad1539a).

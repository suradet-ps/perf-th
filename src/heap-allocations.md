# การจัดสรรหน่วยความจำบนฮีป

การจัดสรรหน่วยความจำบนฮีป (heap allocation) มี overhead และต้นทุนการทำงานพอสมควร แม้รายละเอียดที่แท้จริงจะขึ้นอยู่กับ memory allocator ที่ใช้งานอยู่ แต่โดยทั่วไปแล้ว การจัดสรร (allocation) และการคืนหน่วยความจำ (deallocation) แต่ละครั้งมักเกี่ยวข้องกับการแย่งชิง lock ส่วนกลาง (global lock) การจัดการโครงสร้างข้อมูลภายในที่ซับซ้อน และอาจต้องเรียก system call ของระบบปฏิบัติการด้วย นอกจากนี้ การจัดสรรก้อนเล็กๆ ก็ไม่ได้แปลว่าจะกินเวลาน้อยกว่าการจัดสรรก้อนใหญ่เสมอไป ดังนั้น การเข้าใจว่าโครงสร้างข้อมูลและการทำงานรูปแบบใดใน Rust ที่ทำให้เกิดการจัดสรรหน่วยความจำบนฮีปจึงเป็นเรื่องที่คุ้มค่าอย่างยิ่ง เพราะการหลีกเลี่ยงการจัดสรรที่ไม่จำเป็นจะช่วยเพิ่มประสิทธิภาพของโปรแกรมได้อย่างมหาศาล

เอกสาร [Rust Container Cheat Sheet] มีภาพประกอบจำลองโครงสร้างชนิดข้อมูลที่พบบ่อยใน Rust ไว้อย่างชัดเจน และเป็นคู่มือเสริมที่ยอดเยี่ยมสำหรับศึกษาควบคู่ไปกับหัวข้อต่อไปนี้

[Rust Container Cheat Sheet]: https://docs.google.com/presentation/d/1q-c7UAyrUlM-eZyTo1pd8SZ0qwA_wYxmPZVOQkoDmH4/

## การโปรไฟล์

หากโปรไฟเลอร์อเนกประสงค์รายงานว่าฟังก์ชัน `malloc`, `free` และฟังก์ชันอื่นที่เกี่ยวข้องเป็นคอขวดที่ทำงานหนัก (hot) ก็มักจะคุ้มค่าที่จะลองหาทางลดอัตราการจัดสรรหน่วยความจำ (allocation rate) และ/หรือเปลี่ยนไปใช้ memory allocator ทางเลือก

[DHAT] เป็นโปรไฟเลอร์ชั้นเลิศสำหรับใช้วิเคราะห์เมื่อคุณต้องการลดอัตราการจัดสรรหน่วยความจำ ทำงานได้บน Linux และระบบตระกูล Unix อื่นๆ บางตัว โดย DHAT สามารถระบุตำแหน่งโค้ดที่มีการจัดสรรหน่วยความจำบ่อยเป็นพิเศษและบอกอัตราการจัดสรรได้อย่างแม่นยำ แม้ผลลัพธ์ในแต่ละโปรแกรมจะแตกต่างกันไป แต่จากประสบการณ์ในการพัฒนา rustc พบว่าการลดอัตราการจัดสรรลงเพียง 10 ครั้งต่อทุกๆ 1 ล้านคำสั่ง (instructions executed) ก็สามารถช่วยเพิ่มประสิทธิภาพการทำงานได้อย่างเห็นผลชัดเจน (เช่น เร็วขึ้นราว 1%)

[DHAT]: https://www.valgrind.org/docs/manual/dh-manual.html

## `Box`

[`Box`] เป็นชนิดข้อมูลที่จัดสรรบนฮีปที่เรียบง่ายที่สุด โดยค่า `Box<T>` ก็คือค่าของ `T` ที่ถูกนำไปจัดสรรไว้บนฮีปนั่นเอง

[`Box`]: https://doc.rust-lang.org/std/boxed/struct.Box.html

ในบางกรณี การห่อหุ้มฟิลด์อย่างน้อยหนึ่งฟิลด์ใน struct หรือ enum ด้วย `Box` (boxing) ก็คุ้มค่าที่จะทำ เพื่อช่วยลดขนาดของชนิดข้อมูลนั้นลง (ศึกษารายละเอียดเพิ่มเติมได้ในบท [ขนาดชนิดข้อมูล](type-sizes.md))

นอกเหนือจากกรณีข้างต้นแล้ว `Box` ทำงานตรงไปตรงมาและไม่มีพื้นที่ให้ optimize เพิ่มเติมได้มากนัก

## `Rc`/`Arc`

[`Rc`]/[`Arc`] มีลักษณะคล้ายกับ `Box` แต่ข้อมูลบนฮีปจะมาพร้อมกับตัวนับการอ้างอิง (reference count) สองตัว ทำให้สามารถแชร์ข้อมูลร่วมกันได้ ซึ่งนับเป็นวิธีที่มีประสิทธิภาพในการลดการใช้หน่วยความจำ

[`Rc`]: https://doc.rust-lang.org/std/rc/struct.Rc.html
[`Arc`]: https://doc.rust-lang.org/std/sync/struct.Arc.html

อย่างไรก็ดี หากนำไปใช้กับข้อมูลที่แทบไม่มีการแชร์กันเลย ก็อาจกลายเป็นการเพิ่มอัตราการจัดสรรหน่วยความจำไปโดยปริยาย เพราะต้องจัดสรรข้อมูลบนฮีป ทั้งๆ ที่ข้อมูลนั้นอาจไม่ต้องอยู่บนฮีปเลยก็ได้
[**ตัวอย่าง**](https://github.com/rust-lang/rust/pull/37373/commits/c440a7ae654fb641e68a9ee53b03bf3f7133c2fe)

นอกจากนี้ การเรียก `clone` บนค่า `Rc`/`Arc` จะต่างจาก `Box` ตรงที่ไม่มีการจัดสรรหน่วยความจำใหม่เกิดขึ้น แต่เป็นการเพิ่มค่าตัวนับการอ้างอิง (reference count) ขึ้นหนึ่งเท่านั้น

## `Vec`

[`Vec`] เป็นชนิดข้อมูลที่จัดสรรบนฮีป ซึ่งเปิดโอกาสให้เรา optimize ได้มากมาย ทั้งการลดจำนวนครั้งในการจัดสรร และ/หรือการลดพื้นที่หน่วยความจำที่สูญเปล่าให้เหลือน้อยที่สุด ซึ่งการจะทำเช่นนี้ได้ เราจำเป็นต้องเข้าใจโครงสร้างการจัดเก็บข้อมูลของมันเสียก่อน

[`Vec`]: https://doc.rust-lang.org/std/vec/struct.Vec.html

ตัวแปร `Vec` ประกอบด้วยข้อมูลขนาด 3 word ได้แก่: ความยาว (length), ความจุ (capacity) และพอยน์เตอร์ (pointer) โดยพอยน์เตอร์จะชี้ไปยังพื้นที่หน่วยความจำที่จัดสรรไว้บนฮีป หากความจุไม่เป็นศูนย์และขนาดของ element ไม่เป็นศูนย์ มิฉะนั้นจะไม่ชี้ไปยังหน่วยความจำที่จัดสรรไว้

แม้ว่าตัวโครงสร้าง `Vec` เองจะไม่ได้จัดสรรอยู่บนฮีป (แต่อยู่บนสแต็กหรือใน struct อื่น) แต่สมาชิก (elements) ของมัน (หากมี และไม่ได้มีขนาดเป็นศูนย์) จะถูกจัดสรรไว้บนฮีปเสมอ และพื้นที่หน่วยความจำที่เตรียมไว้สำหรับเก็บสมาชิกเหล่านั้นอาจมีขนาดใหญ่เกินกว่าจำนวนสมาชิกที่มีอยู่จริง เพื่อเผื่อพื้นที่ไว้รองรับสมาชิกใหม่ที่จะเพิ่มเข้ามาในอนาคต โดยจำนวนสมาชิกที่มีอยู่จริงในปัจจุบันจะเรียกว่า ความยาว (length) ส่วนจำนวนสมาชิกสูงสุดที่สามารถบรรจุได้โดยไม่ต้องจัดสรรหน่วยความจำใหม่ จะเรียกว่า ความจุ (capacity)

เมื่อเวกเตอร์จำเป็นต้องขยายขนาดเกินกว่าความจุที่มีอยู่ สมาชิกเดิมทั้งหมดจะถูกคัดลอกไปยังพื้นที่หน่วยความจำบนฮีปแห่งใหม่ที่มีขนาดใหญ่ขึ้น แล้วหน่วยความจำฮีปเดิมจะถูกคืนพื้นที่ (deallocate)

### การเติบโตของ `Vec`

ตัวแปร `Vec` ใหม่ที่ว่างเปล่า ซึ่งสร้างขึ้นผ่านวิธีมาตรฐานทั่วไป ([`vec![]`](https://doc.rust-lang.org/std/macro.vec.html) หรือ [`Vec::new`] หรือ [`Vec::default`]) จะมีความยาวและความจุเป็นศูนย์ จึงไม่ต้องจัดสรรหน่วยความจำบนฮีปเลย แต่หากคุณ push สมาชิกทีละตัวต่อท้าย `Vec` ไปเรื่อยๆ มันจะจัดสรรหน่วยความจำใหม่ (reallocate) เป็นระยะๆ แม้กลยุทธ์การขยายขนาด (growth strategy) จะไม่ได้ถูกระบุไว้เป็นกฎตายตัว แต่ ณ เวลาที่เขียนหนังสือเล่มนี้ ตัวคอมไพเลอร์ใช้กลยุทธ์แบบเพิ่มขึ้นเกือบเท่าตัว ซึ่งทำให้เกิดลำดับความจุดังนี้: 0, 4, 8, 16, 32, 64 ไปเรื่อยๆ (ข้ามจาก 0 ไป 4 โดยตรงโดยไม่ผ่าน 1 และ 2 เพราะในทางปฏิบัติวิธีนี้ช่วย [หลีกเลี่ยงการจัดสรรหลายครั้ง]) เมื่อเวกเตอร์โตขึ้น ความถี่ในการจัดสรรหน่วยความจำใหม่จะลดลงแบบเอกซ์โพเนนเชียล แต่ในขณะเดียวกัน ปริมาณความจุส่วนเกินที่อาจถูกปล่อยทิ้งไว้โดยเปล่าประโยชน์ก็จะเพิ่มขึ้นแบบเอกซ์โพเนนเชียลเช่นกัน

[`Vec::new`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.new
[`Vec::default`]: https://doc.rust-lang.org/std/default/trait.Default.html#tymethod.default
[หลีกเลี่ยงการจัดสรรหลายครั้ง]: https://github.com/rust-lang/rust/pull/72227

กลยุทธ์การขยายขนาดเช่นนี้ถือเป็นมาตรฐานสำหรับโครงสร้างข้อมูลที่ขยายขนาดได้ และมีความสมเหตุสมผลสำหรับกรณีการใช้งานทั่วไป แต่หากคุณทราบขนาดความยาวโดยประมาณของเวกเตอร์ล่วงหน้า คุณก็มักจะทำได้ดีกว่านี้มาก หากคุณมีจุดจัดสรรเวกเตอร์ที่ทำงานหนัก (เช่น มีการเรียก [`Vec::push`] ซ้ำๆ ใน hot path) การใช้คำสั่ง [`eprintln!`] พิมพ์ความยาวของเวกเตอร์ ณ ตำแหน่งนั้นออกมา แล้วนำข้อมูลมาวิเคราะห์ต่อ (เช่น ใช้เครื่องมือ [`counts`]) เพื่อดูการกระจายตัวของความยาว (length distribution) ย่อมคุ้มค่าที่จะทำ ตัวอย่างเช่น คุณอาจพบว่ามีเวกเตอร์สั้นๆ จำนวนมหาศาล หรือมีเวกเตอร์ขนาดยาวมากๆ ในจำนวนน้อย ซึ่งแนวทางที่ดีที่สุดในการ optimize จุดจัดสรรหน่วยความจำนั้นๆ จะแตกต่างกันไปตามแต่ละกรณี

[`Vec::push`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.push
[`eprintln!`]: https://doc.rust-lang.org/std/macro.eprintln.html
[`counts`]: https://github.com/nnethercote/counts/

### `Vec` ขนาดสั้น

หากโปรแกรมของคุณมีเวกเตอร์ขนาดสั้นเป็นจำนวนมาก คุณสามารถเปลี่ยนไปใช้ชนิดข้อมูล `SmallVec` จาก crate [`smallvec`] ได้ โดย `SmallVec<[T; N]>` สามารถนำมาใช้แทน `Vec` ได้ทันที (drop-in replacement) ซึ่งมันสามารถเก็บสมาชิกได้ถึง `N` ตัวไว้ภายในโครงสร้าง `SmallVec` เอง แล้วจึงสลับไปจัดสรรบนฮีปหากจำนวนสมาชิกเกินกว่านั้น (ทั้งนี้ต้องเปลี่ยน macro จาก `vec![]` เป็น `smallvec![]` ด้วย)
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/50565/commits/78262e700dc6a7b57e376742f344e80115d2d3f2),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/55383/commits/526dc1421b48e3ee8357d58d997e7a0f4bb26915)

[`smallvec`]: https://crates.io/crates/smallvec

`SmallVec` ช่วยลดอัตราการจัดสรรหน่วยความจำได้อย่างเห็นผลเมื่อใช้อย่างเหมาะสม ทว่าการนำมาใช้ไม่ได้การันตีว่าจะได้ประสิทธิภาพที่ดีขึ้นเสมอไป เพราะมันอาจทำงานช้ากว่า `Vec` เล็กน้อยสำหรับการดำเนินการทั่วไป เนื่องจากต้องคอยตรวจสอบอยู่เสมอว่าสมาชิกถูกจัดสรรบนฮีปหรือไม่ นอกจากนี้ หากค่า `N` มีขนาดใหญ่ หรือ `T` มีขนาดใหญ่ ตัวโครงสร้าง `SmallVec<[T; N]>` เองก็อาจมีขนาดใหญ่กว่า `Vec<T>` ส่งผลให้การคัดลอกค่า `SmallVec` ช้าลงตามไปด้วย ดังนั้น คุณจึงต้องทำเบนช์มาร์กเพื่อยืนยันเสมอว่าการปรับแต่งนี้ช่วยเพิ่มความเร็วได้จริง

หากคุณมีเวกเตอร์ขนาดสั้นเป็นจำนวนมาก *และ* ทราบความยาวสูงสุดของมันอย่างแน่นอน ชนิดข้อมูล `ArrayVec` จาก crate [`arrayvec`] จะเป็นตัวเลือกที่เหมาะสมยิ่งกว่า `SmallVec` เนื่องจากมันไม่มีกลไกสำรองที่ต้องสลับไปจัดสรรบนฮีปเลย จึงทำงานได้เร็วกว่าเล็กน้อย
[**ตัวอย่าง**](https://github.com/rust-lang/rust/pull/74310/commits/c492ca40a288d8a85353ba112c4d38fe87ef453e)

[`arrayvec`]: https://crates.io/crates/arrayvec

### `Vec` ขนาดยาว

## `clone`

การเรียก [`clone`] บนค่าที่มีหน่วยความจำจัดสรรบนฮีปอยู่ภายใน มักเกี่ยวข้องกับการจัดสรรเพิ่มเติม ตัวอย่างเช่น การเรียก `clone` บน `Vec` ที่มีข้อมูลอยู่ จะต้องจัดสรรใหม่สำหรับเก็บสำเนาของสมาชิกเหล่านั้น (แต่โปรดสังเกตว่าความจุของ `Vec` ใหม่ อาจไม่เท่ากับความจุของ `Vec` เดิม) ข้อยกเว้นคือ `Rc`/`Arc` ซึ่งการเรียก `clone` เพียงเพิ่มตัวนับการอ้างอิงเท่านั้น

[`clone`]: https://doc.rust-lang.org/std/clone/trait.Clone.html#tymethod.clone

[`clone_from`] เป็นทางเลือกแทน `clone` โดย `a.clone_from(&b)` ให้ผลลัพธ์เทียบเท่ากับ `a = b.clone()` แต่ช่วยหลีกเลี่ยงการจัดสรรที่ไม่จำเป็นได้ ตัวอย่างเช่น หากคุณต้องการโคลน `Vec` หนึ่งทับลงบน `Vec` เดิมที่มีอยู่แล้ว หน่วยความจำฮีปของ `Vec` เดิมจะถูกนำกลับมาใช้ใหม่หากเป็นไปได้ ดังที่ตัวอย่างต่อไปนี้แสดง:
```rust
let mut v1: Vec<u32> = Vec::with_capacity(99);
let v2: Vec<u32> = vec![1, 2, 3];
v1.clone_from(&v2); // v1's allocation is reused
assert_eq!(v1.capacity(), 99);
```
แม้ว่า `clone` มักทำให้เกิดการจัดสรร แต่ก็เป็นสิ่งที่สมเหตุสมผลที่จะใช้ในหลายสถานการณ์ และมักทำให้โค้ดเรียบง่ายขึ้น ใช้ข้อมูลการทำ profiling เพื่อดูว่าการเรียก `clone` จุดใดที่ทำงานหนัก (hot) และคุ้มค่าที่จะลงแรงหลีกเลี่ยง

[`clone_from`]: https://doc.rust-lang.org/std/clone/trait.Clone.html#method.clone_from

บางครั้งโค้ด Rust ก็มีการเรียก `clone` ที่ไม่จำเป็นหลงเหลืออยู่ เนื่องจาก (ก) ความผิดพลาดของโปรแกรมเมอร์ หรือ (ข) การเปลี่ยนแปลงในโค้ดที่ทำให้การเรียก `clone` ซึ่งเคยจำเป็นกลายเป็นไม่จำเป็น หากคุณเห็นการเรียก `clone` ใน hot path ซึ่งดูเหมือนไม่จำเป็น บางครั้งมันก็อาจถูกลบออกได้เลย
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/37318/commits/e382267cfb9133ef12d59b66a2935ee45b546a61),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/37705/commits/11c1126688bab32f76dbe1a973906c7586da143f),
[**ตัวอย่างที่ 3**](https://github.com/rust-lang/rust/pull/64302/commits/36b37e22de92b584b9cf4464ed1d4ad317b798be)

## `to_owned`

[`ToOwned::to_owned`] ถูก implement ให้กับชนิดข้อมูลทั่วไปหลายชนิด โดยทำหน้าที่สร้างข้อมูลแบบเป็นเจ้าของ (owned data) จากข้อมูลแบบยืม (borrowed data) ซึ่งมักทำผ่านการโคลน จึงมักทำให้เกิดการจัดสรรบนฮีป ตัวอย่างเช่น มันใช้สร้าง `String` จาก `&str` ได้

[`ToOwned::to_owned`]: https://doc.rust-lang.org/std/borrow/trait.ToOwned.html#tymethod.to_owned

บางครั้งการเรียก `to_owned` (และการเรียกที่เกี่ยวข้อง เช่น `clone` และ `to_string`) สามารถหลีกเลี่ยงได้โดยเก็บการอ้างอิง (reference) ไปยังข้อมูลแบบยืมไว้ใน struct แทนที่จะเก็บสำเนาแบบเป็นเจ้าของ วิธีนี้จำเป็นต้องมี lifetime annotation บน struct ซึ่งทำให้โค้ดซับซ้อนขึ้น และควรทำเฉพาะเมื่อการทำ profiling และเบนช์มาร์กแสดงว่าคุ้มค่าเท่านั้น
[**ตัวอย่าง**](https://github.com/rust-lang/rust/pull/50855/commits/6872377357dbbf373cfd2aae352cb74cfcc66f34)

## `Cow`

บางครั้งโค้ดต้องจัดการกับข้อมูลผสมระหว่างแบบยืมและแบบเป็นเจ้าของ ลองนึกภาพเวกเตอร์ของข้อความแสดงข้อผิดพลาด ซึ่งบางส่วนเป็นสตริงลิเทอรัลแบบสแตติกและบางส่วนสร้างด้วย `format!` การแทนค่าที่ตรงไปตรงมาคือ `Vec<String>` ดังตัวอย่างต่อไปนี้:
```rust
let mut errors: Vec<String> = vec![];
errors.push("something went wrong".to_string());
errors.push(format!("something went wrong on line {}", 100));
```
วิธีนี้ต้องเรียก `to_string` เพื่อแปลงสตริงลิเทอรัลแบบสแตติกให้เป็น `String` ซึ่งก่อให้เกิดการจัดสรรบนฮีป

แต่คุณสามารถใช้ชนิดข้อมูล [`Cow`] แทนได้ ซึ่งเก็บได้ทั้งข้อมูลแบบยืมและแบบเป็นเจ้าของ โดยค่าแบบยืม `x` จะถูกห่อด้วย `Cow::Borrowed(x)` และค่าแบบเป็นเจ้าของ `y` จะถูกห่อด้วย `Cow::Owned(y)` นอกจากนี้ `Cow` ยัง implement trait `From<T>` สำหรับชนิดสตริง, สไลซ์ และ path ต่างๆ ดังนั้นคุณจึงมักใช้ `into` ได้เช่นกัน (หรือใช้ `Cow::from` ซึ่งยาวกว่าแต่ทำให้โค้ดอ่านง่ายกว่า เพราะระบุชนิดข้อมูลได้ชัดเจนขึ้น) ตัวอย่างต่อไปนี้นำทุกอย่างมารวมกัน:

[`Cow`]: https://doc.rust-lang.org/std/borrow/enum.Cow.html

```rust
use std::borrow::Cow;
let mut errors: Vec<Cow<'static, str>> = vec![];
errors.push(Cow::Borrowed("something went wrong"));
errors.push(Cow::Owned(format!("something went wrong on line {}", 100)));
errors.push(Cow::from("something else went wrong"));
errors.push(format!("something else went wrong on line {}", 101).into());
```
ตอนนี้ `errors` สามารถเก็บข้อมูลผสมระหว่างแบบยืมและแบบเป็นเจ้าของได้โดยไม่ต้องจัดสรรเพิ่มเติมสำหรับข้อความสแตติกเลย ตัวอย่างนี้ใช้ `&str`/`String` แต่คู่อื่นๆ เช่น `&[T]`/`Vec<T>` และ `&Path`/`PathBuf` ก็สามารถทำได้เช่นกัน
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/37064/commits/b043e11de2eb2c60f7bfec5e15960f537b229e20),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/56336/commits/787959c20d062d396b97a5566e0a766d963af022)

ทั้งหมดที่กล่าวมาข้างต้นใช้ได้เมื่อข้อมูลไม่ถูกแก้ไข แต่ `Cow` ยังอนุญาตให้ยกระดับข้อมูลแบบยืมเป็นข้อมูลแบบเป็นเจ้าของได้หากจำเป็นต้องแก้ไข โดย [`Cow::to_mut`] จะขอ mutable reference ไปยังค่าแบบเป็นเจ้าของ ซึ่งจะโคลนข้อมูลหากจำเป็น พฤติกรรมนี้เรียกว่า "clone-on-write" ซึ่งเป็นที่มาของชื่อ `Cow`

[`Deref`]: https://doc.rust-lang.org/std/ops/trait.Deref.html
[`Cow::to_mut`]: https://doc.rust-lang.org/std/borrow/enum.Cow.html#method.to_mut

พฤติกรรม clone-on-write นี้มีประโยชน์เมื่อคุณมีข้อมูลแบบยืม เช่น `&str` ที่ส่วนใหญ่อ่านอย่างเดียว แต่บางครั้งต้องแก้ไข
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/50855/commits/ad471452ba6fbbf91ad566dc4bdf1033a7281811),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/68848/commits/67da45f5084f98eeb20cc6022d68788510dc832a)

สุดท้าย เพราะ `Cow` implement [`Deref`] คุณจึงเรียกเมธอดบนข้อมูลที่มันห่อหุ้มได้โดยตรง

`Cow` อาจดูจุกจิกในการทำให้ใช้งานได้ แต่ก็มักคุ้มค่ากับความพยายาม

## การนำคอลเลกชันกลับมาใช้ซ้ำ

บางครั้งคุณต้องสร้างคอลเลกชันอย่าง `Vec` ขึ้นมาเป็นขั้นตอน โดยปกติแล้วการทำเช่นนี้โดยแก้ไข `Vec` ตัวเดียวจะดีกว่าการสร้าง `Vec` หลายตัวแล้วนำมารวมกันในภายหลัง

ตัวอย่างเช่น หากคุณมีฟังก์ชัน `do_stuff` ที่สร้าง `Vec` ออกมาและอาจถูกเรียกหลายครั้ง:
```rust
fn do_stuff(x: u32, y: u32) -> Vec<u32> {
    vec![x, y]
}
```
การแก้ไข `Vec` ที่ส่งเข้ามาแทนอาจดีกว่า:
```rust
fn do_stuff(x: u32, y: u32, vec: &mut Vec<u32>) {
    vec.push(x);
    vec.push(y);
}
```
บางครั้งการเก็บคอลเลกชันตัวทำงานหลัก (workhorse) ไว้ใช้ซ้ำก็คุ้มค่า ตัวอย่างเช่น หากต้องใช้ `Vec` ในแต่ละรอบของลูป คุณอาจประกาศ `Vec` ไว้นอกลูป ใช้มันภายในเนื้อลูป แล้วเรียก [`clear`] ที่ท้ายเนื้อลูป (เพื่อล้าง `Vec` โดยไม่กระทบความจุของมัน) วิธีนี้หลีกเลี่ยงการจัดสรรได้ แลกกับการทำให้เห็นไม่ชัดเจนว่าการใช้ `Vec` ในแต่ละรอบไม่เกี่ยวข้องกัน
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/77990/commits/45faeb43aecdc98c9e3f2b24edf2ecc71f39d323),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/51870/commits/b0c78120e3ecae5f4043781f7a3f79e2277293e7)

[`clear`]: https://doc.rust-lang.org/std/vec/struct.Vec.html#method.clear

ในทำนองเดียวกัน บางครั้งการเก็บคอลเลกชันตัวทำงานหลักไว้ใน struct เพื่อใช้ซ้ำในเมธอดหนึ่งหรือหลายเมธอดที่ถูกเรียกซ้ำๆ ก็คุ้มค่า

## การอ่านไฟล์ทีละบรรทัด

[`BufRead::lines`] ทำให้การอ่านไฟล์ทีละบรรทัดเป็นเรื่องง่าย:
```rust
# fn blah() -> Result<(), std::io::Error> {
# fn process(_: &str) {}
use std::io::{self, BufRead};
let mut lock = io::stdin().lock();
for line in lock.lines() {
    process(&line?);
}
# Ok(())
# }
```
แต่อิเทอเรเตอร์ที่มันสร้างขึ้นคืนค่า `io::Result<String>` ซึ่งหมายความว่ามันจัดสรรหน่วยความจำใหม่ทุกบรรทัดในไฟล์

[`BufRead::lines`]: https://doc.rust-lang.org/stable/std/io/trait.BufRead.html#method.lines

ทางเลือกหนึ่งคือใช้ `String` ตัวทำงานหลักในลูปที่วนเรียก
[`BufRead::read_line`]:
```rust
# fn blah() -> Result<(), std::io::Error> {
# fn process(_: &str) {}
use std::io::{self, BufRead};
let mut lock = io::stdin().lock();
let mut line = String::new();
while lock.read_line(&mut line)? != 0 {
    process(&line);
    line.clear();
}
# Ok(())
# }
```
วิธีนี้ลดจำนวนครั้งในการจัดสรรลงเหลือไม่เกินหยิบมือ และอาจเหลือเพียงครั้งเดียว (จำนวนที่แน่นอนขึ้นอยู่กับว่าต้องจัดสรร `line` ใหม่กี่ครั้ง ซึ่งขึ้นอยู่กับการกระจายตัวของความยาวบรรทัดในไฟล์)

วิธีนี้จะใช้ได้เฉพาะเมื่อเนื้อลูปทำงานกับ `&str` ได้ ไม่ใช่ `String`

[`BufRead::read_line`]: https://doc.rust-lang.org/stable/std/io/trait.BufRead.html#method.read_line

## การป้องกันการถดถอยของประสิทธิภาพ

เพื่อให้แน่ใจว่าจำนวนและ/หรือขนาดของการจัดสรรที่โค้ดของคุณทำจะไม่เพิ่มขึ้นโดยไม่ตั้งใจ คุณสามารถใช้ฟีเจอร์ *การทดสอบการใช้ฮีป (heap usage testing)* ของ [dhat-rs] เขียนเทสต์ที่ตรวจสอบว่าโค้ดบางส่วนจัดสรรหน่วยความจำฮีปในปริมาณที่คาดหวังไว้

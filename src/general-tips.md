# เคล็ดลับทั่วไป

หัวข้อก่อนหน้าของหนังสือเล่มนี้ได้กล่าวถึงเทคนิคเฉพาะของ Rust ไปแล้ว หัวข้อนี้ให้ภาพรวมสั้นๆ ของหลักการทั่วไปด้านประสิทธิภาพบางประการ

ตราบใดที่หลีกเลี่ยงกับดักที่เห็นได้ชัด (เช่น[การใช้บิลด์ที่ไม่ใช่รีลีส]) โค้ด Rust โดยทั่วไปก็เร็วและใช้หน่วยความจำน้อย โดยเฉพาะอย่างยิ่งหากคุณคุ้นเคยกับภาษาที่มีชนิดข้อมูลแบบไดนามิกอย่าง Python และ Ruby หรือภาษาที่มีชนิดข้อมูลแบบสแตติกพร้อมตัวเก็บขยะอย่าง Java และ C#

[การใช้บิลด์ที่ไม่ใช่รีลีส]: build-configuration.md

โค้ดที่เพิ่มประสิทธิภาพแล้วมักซับซ้อนกว่าและต้องใช้ความพยายามมากกว่าในการเขียนโค้ดที่ไม่เพิ่มประสิทธิภาพ ด้วยเหตุนี้ จึงคุ้มค่าที่จะเพิ่มประสิทธิภาพเฉพาะโค้ดฮอตเท่านั้น

การปรับปรุงประสิทธิภาพที่ใหญ่ที่สุดมักมาจากการเปลี่ยนอัลกอริทึมหรือโครงสร้างข้อมูล มากกว่าการเพิ่มประสิทธิภาพระดับต่ำ
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/53383/commits/5745597e6195fe0591737f242d02350001b6c590),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/54318/commits/154be2c98cf348de080ce951df3f73649e8bb1a6).

การเขียนโค้ดที่ทำงานร่วมกับฮาร์ดแวร์สมัยใหม่ได้ดีนั้นไม่ง่ายเสมอไป แต่ก็คุ้มค่าที่จะพยายาม ตัวอย่างเช่น พยายามลดแคชพลาดและการทำนายทิศทางผิดพลาดให้เหลือน้อยที่สุดเมื่อเป็นไปได้

การเพิ่มประสิทธิภาพส่วนใหญ่ให้ความเร็วที่เพิ่มขึ้นเล็กน้อย แม้ว่าการเพิ่มความเร็วเล็กน้อยเพียงอย่างเดียวจะไม่รู้สึกได้ แต่ผลรวมของมันจะชัดเจนมากหากคุณทำได้มากพอ

โปรไฟเลอร์แต่ละตัวมีจุดแข็งต่างกัน การใช้มากกว่าหนึ่งตัวเป็นสิ่งที่ดี

เมื่อการโปรไฟล์บ่งชี้ว่าฟังก์ชันหนึ่งฮอต มีวิธีทั่วไปสองวิธีในการเพิ่มความเร็ว: (ก) ทำให้ฟังก์ชันเร็วขึ้น และ/หรือ (ข) หลีกเลี่ยงการเรียกมันบ่อยเท่านั้น

การขจัดจุดที่ทำให้ช้าอย่างไม่เข้าท่ามักทำได้ง่ายกว่าการเพิ่มความเร็วด้วยเทคนิคฉลาดๆ

หลีกเลี่ยงการคำนวณสิ่งต่างๆ เว้นแต่จำเป็น การคำนวณแบบขี้เกียจ/ตามต้องการมักให้ผลดี
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/36592/commits/80a44779f7a211e075da9ed0ff2763afa00f43dc),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/50339/commits/989815d5670826078d9984a3515eeb68235a4687).

กรณีทั่วไปที่ซับซ้อนมักหลีกเลี่ยงได้ด้วยการตรวจสอบกรณีพิเศษที่พบบ่อยและเรียบง่ายกว่าอย่างคาดหวังเชิงบวก (optimistically)
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/68790/commits/d62b6f204733d255a3e943388ba99f14b053bf4a),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/53733/commits/130e55665f8c9f078dec67a3e92467853f400250),
[**ตัวอย่างที่ 3**](https://github.com/rust-lang/rust/pull/65260/commits/59e41edcc15ed07de604c61876ea091900f73649).
โดยเฉพาะอย่างยิ่ง การจัดการคอลเลกชันที่มี 0, 1 หรือ 2 องค์ประกอบเป็นกรณีพิเศษมักให้ผลดีเมื่อขนาดเล็กเป็นส่วนใหญ่
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/50932/commits/2ff632484cd8c2e3b123fbf52d9dd39b54a94505),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/64627/commits/acf7d4dcdba4046917c61aab141c1dec25669ce9),
[**ตัวอย่างที่ 3**](https://github.com/rust-lang/rust/pull/64949/commits/14192607d38f5501c75abea7a4a0e46349df5b5f),
[**ตัวอย่างที่ 4**](https://github.com/rust-lang/rust/pull/64949/commits/d1a7bb36ad0a5932384eac03d3fb834efc0317e5).

ในทำนองเดียวกัน เมื่อจัดการกับข้อมูลที่มีการซ้ำกัน บ่อยครั้งสามารถใช้การบีบอัดข้อมูลรูปแบบง่ายๆ ได้ โดยใช้การแทนค่าที่กะทัดรัดสำหรับค่าที่พบบ่อย แล้วมีตารางสำรองสำหรับค่าที่ไม่ค่อยพบเป็นทางถอย
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/54420/commits/b2f25e3c38ff29eebe6c8ce69b8c69243faa440d),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/59693/commits/fd7f605365b27bfdd3cd6763124e81bddd61dd28),
[**ตัวอย่างที่ 3**](https://github.com/rust-lang/rust/pull/65750/commits/eea6f23a0ed67fd8c6b8e1b02cda3628fee56b2f).

เมื่อโค้ดต้องจัดการหลายกรณี ให้วัดความถี่ของแต่ละกรณีและจัดการกรณีที่พบบ่อยที่สุดก่อน

เมื่อจัดการกับการค้นหาที่มี locality สูง การวางแคชขนาดเล็กไว้หน้าโครงสร้างข้อมูลอาจให้ผลดี

โค้ดที่เพิ่มประสิทธิภาพแล้วมักมีโครงสร้างที่ไม่ชัดเจน ซึ่งหมายความว่าคอมเมนต์อธิบายมีคุณค่า โดยเฉพาะคอมเมนต์ที่อ้างอิงผลการวัดจากการโปรไฟล์ คอมเมนต์อย่าง "99% ของเวลา เวกเตอร์นี้มี 0 หรือ 1 องค์ประกอบ จึงจัดการกรณีเหล่านั้นก่อน" ให้ความกระจ่างได้

# เคล็ดลับทั่วไป

บทก่อนๆ ของหนังสือเล่มนี้เน้นเทคนิคเฉพาะสำหรับภาษา Rust เป็นหลัก ในบทนี้จะเป็นภาพรวมสั้นๆ ของหลักการทั่วไปในการเพิ่มประสิทธิภาพ

ตราบใดที่หลีกเลี่ยงข้อผิดพลาดที่เห็นได้ชัด (เช่น [การใช้บิลด์ที่ไม่ใช่รีลีส]) โดยทั่วไปแล้วโค้ดภาษา Rust จะทำงานได้รวดเร็วและใช้หน่วยความจำน้อยอยู่แล้ว โดยเฉพาะเมื่อเทียบกับภาษาที่มีระบบชนิดข้อมูลแบบไดนามิกอย่าง Python และ Ruby หรือภาษาที่มีระบบชนิดข้อมูลแบบสแตติกแต่ใช้ Garbage Collector อย่าง Java และ C#

[การใช้บิลด์ที่ไม่ใช่รีลีส]: build-configuration.md

โค้ดที่ผ่านการเพิ่มประสิทธิภาพ (optimize) มักมีความซับซ้อนและต้องใช้แรงในการเขียนมากกว่าโค้ดทั่วไป ด้วยเหตุนี้ จึงควรเลือก optimize เฉพาะโค้ดส่วนที่ทำงานหนัก (hot code) เท่านั้น

การยกระดับประสิทธิภาพครั้งใหญ่ที่สุด มักเกิดจากการปรับเปลี่ยนอัลกอริทึมหรือโครงสร้างข้อมูล มากกว่าการไล่ optimize ในระดับ low-level
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/53383/commits/5745597e6195fe0591737f242d02350001b6c590),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/54318/commits/154be2c98cf348de080ce951df3f73649e8bb1a6).

การเขียนโค้ดที่ทำงานสอดรับกับสถาปัตยกรรมของฮาร์ดแวร์สมัยใหม่ไม่ใช่เรื่องง่ายเสมอไป แต่ก็คุ้มค่าที่จะลงแรง เช่น พยายามลด cache misses และ branch mispredictions ให้เหลือน้อยที่สุดเท่าที่จะทำได้

การ optimize ส่วนใหญ่ช่วยให้โค้ดเร็วขึ้นทีละเล็กทีละน้อย แม้ความเร็วที่เพิ่มขึ้นในแต่ละจุดอาจดูไม่ชัดเจน แต่เมื่อนำมารวมกันหลายๆ จุด ก็จะส่งผลต่อประสิทธิภาพโดยรวมอย่างมหาศาล

โปรไฟเลอร์แต่ละตัวมีจุดเด่นและข้อจำกัดที่แตกต่างกัน การเลือกใช้โปรไฟเลอร์มากกว่าหนึ่งตัวร่วมกันจึงเป็นแนวทางที่ดีเสมอ

เมื่อการโปรไฟล์ชี้ว่ามีฟังก์ชันใดทำงานหนักเป็นพิเศษ มี 2 แนวทางหลักในการเร่งความเร็ว: (ก) ปรับแต่งฟังก์ชันนั้นให้ทำงานเร็วขึ้น และ/หรือ (ข) ลดจำนวนครั้งในการเรียกใช้ฟังก์ชันนั้นให้น้อยลง

การกำจัดจุดที่ทำให้โปรแกรมช้าโดยไม่จำเป็น มักทำได้ง่ายกว่าการพยายามคิดค้นเทคนิคเพิ่มความเร็วที่ซับซ้อนแยบยล

หลีกเลี่ยงการประมวลผลสิ่งใดก็ตามจนกว่าจะจำเป็นจริงๆ การคำนวณแบบ lazy หรือคำนวณเมื่อต้องการใช้จริง (on-demand) มักช่วยให้โปรแกรมมีประสิทธิภาพดีขึ้นอย่างเห็นได้ชัด
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/36592/commits/80a44779f7a211e075da9ed0ff2763afa00f43dc),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/50339/commits/989815d5670826078d9984a3515eeb68235a4687).

เราสามารถหลีกเลี่ยงการประมวลผลกรณีทั่วไปที่ซับซ้อนได้ โดยการดักตรวจจับกรณีพิเศษที่พบบ่อยและเรียบง่ายกว่าก่อน (optimistic check)
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/68790/commits/d62b6f204733d255a3e943388ba99f14b053bf4a),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/53733/commits/130e55665f8c9f078dec67a3e92467853f400250),
[**ตัวอย่างที่ 3**](https://github.com/rust-lang/rust/pull/65260/commits/59e41edcc15ed07de604c61876ea091900f73649).
โดยเฉพาะอย่างยิ่ง หากข้อมูลส่วนใหญ่มีขนาดเล็ก การแยกจัดการคอลเลกชันที่มี 0, 1 หรือ 2 สมาชิกเป็นกรณีพิเศษ มักให้ผลลัพธ์ที่คุ้มค่ามาก
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/50932/commits/2ff632484cd8c2e3b123fbf52d9dd39b54a94505),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/64627/commits/acf7d4dcdba4046917c61aab141c1dec25669ce9),
[**ตัวอย่างที่ 3**](https://github.com/rust-lang/rust/pull/64949/commits/14192607d38f5501c75abea7a4a0e46349df5b5f),
[**ตัวอย่างที่ 4**](https://github.com/rust-lang/rust/pull/64949/commits/d1a7bb36ad0a5932384eac03d3fb834efc0317e5).

ในทำนองเดียวกัน เมื่อต้องจัดการกับข้อมูลที่มีรูปแบบซ้ำๆ เราสามารถใช้เทคนิคบีบอัดข้อมูลแบบง่ายๆ ได้ โดยจัดเก็บค่าที่พบบ่อยในรูปแบบที่กะทัดรัด และค่อยเปิดตารางสำรอง (secondary table) เมื่อพบค่าพิเศษที่ไม่ค่อยเกิดขึ้น
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/54420/commits/b2f25e3c38ff29eebe6c8ce69b8c69243faa440d),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/59693/commits/fd7f605365b27bfdd3cd6763124e81bddd61dd28),
[**ตัวอย่างที่ 3**](https://github.com/rust-lang/rust/pull/65750/commits/eea6f23a0ed67fd8c6b8e1b02cda3628fee56b2f).

เมื่อโค้ดต้องรองรับหลายกรณี ให้วัดความถี่ของการเกิดแต่ละกรณี แล้วจัดลำดับให้จัดการกรณีที่พบบ่อยที่สุดก่อนเสมอ

สำหรับการค้นหาข้อมูลที่มี locality สูง (การเข้าถึงข้อมูลเดิมซ้ำๆ หรือตำแหน่งใกล้เคียงกัน) การวางแคชขนาดเล็กไว้หน้าโครงสร้างข้อมูลมักช่วยเพิ่มประสิทธิภาพได้เป็นอย่างดี

โค้ดที่ผ่านการ optimize มักมีโครงสร้างที่เข้าใจยากและไม่ตรงไปตรงมา การเขียนคอมเมนต์อธิบายเหตุผลจึงมีคุณค่าอย่างยิ่ง โดยเฉพาะคอมเมนต์ที่อ้างอิงตัวเลขจากการทำ profiling เช่น "99% ของกรณี เวกเตอร์นี้มีสมาชิกเพียง 0 หรือ 1 ตัว จึงจัดการกรณีเหล่านี้ก่อน" ซึ่งจะช่วยให้ผู้ดูแลโค้ดเข้าใจได้อย่างชัดเจน

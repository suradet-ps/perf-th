# เวลาในการคอมไพล์

แม้ว่าหนังสือเล่มนี้จะเน้นเรื่องการปรับปรุงประสิทธิภาพของโปรแกรม Rust เป็นหลัก แต่หัวข้อนี้ว่าด้วยการลดเวลาในการคอมไพล์ของโปรแกรม Rust เพราะเป็นหัวข้อที่เกี่ยวข้องและมีผู้คนสนใจเป็นจำนวนมาก

หัวข้อ[การลดเวลาในการคอมไพล์] ได้กล่าวถึงวิธีลดเวลาในการคอมไพล์ผ่านตัวเลือกการตั้งค่าการบิลด์ ส่วนที่เหลือของหัวข้อนี้อธิบายวิธีลดเวลาในการคอมไพล์ที่ต้องแก้ไขโค้ดของโปรแกรม

[การลดเวลาในการคอมไพล์]: build-configuration.md#การลดเวลาในการคอมไพล

สำหรับเทคนิคการลดเวลาในการคอมไพล์เพิ่มเติม โปรดดูรายการ[เคล็ดลับการลดเวลาในการคอมไพล์ Rust][Tips] ที่ครอบคลุมของ Corrode

[Tips]: https://corrode.dev/blog/tips-for-faster-rust-compile-times/

## การแสดงภาพการคอมไพล์

Cargo มีฟีเจอร์ที่ช่วยให้คุณเห็นภาพการคอมไพล์โปรแกรมของคุณได้ บิลด์ด้วยคำสั่งนี้:
```text
cargo build --timings
```
เมื่อเสร็จสิ้น มันจะพิมพ์ชื่อไฟล์ HTML ออกมา เปิดไฟล์นั้นในเว็บเบราว์เซอร์ ภายในมี[แกนต์ชาร์ต (Gantt chart)][Gantt chart] ที่แสดงความสัมพันธ์แบบพึ่งพาอาศัยกันระหว่างเครตต่างๆ ในโปรแกรมของคุณ ซึ่งแสดงให้เห็นว่ากราฟเครตของคุณมีศักยภาพในการประมวลผลแบบขนานมากเพียงใด และอาจบ่งชี้ว่าควรแยกเครตขนาดใหญ่ที่ทำให้การคอมไพล์ต้องรอเป็นลำดับออกหรือไม่ ดู[เอกสารประกอบ][timings] สำหรับรายละเอียดเพิ่มเติมเกี่ยวกับวิธีอ่านกราฟ

[Gantt chart]: https://en.wikipedia.org/wiki/Gantt_chart
[timings]: https://doc.rust-lang.org/nightly/cargo/reference/timings.html

## มาโคร

มาโครบางตัวสร้างโค้ดออกมาจำนวนมาก ซึ่งโค้ดนั้นต้องใช้เวลาในการคอมไพล์ แฟล็ก `-Zmacro-stats` ของคอมไพเลอร์ Rust ช่วยระบุกรณีเช่นนี้ได้

ตัวอย่างเช่น หากคุณต้องการวัดเฉพาะลีฟเครต (leaf crate) ของโปรเจกต์:
```text
cargo +nightly rustc -- -Zmacro-stats
```
คอมไพเลอร์จะพิมพ์ข้อมูลเกี่ยวกับปริมาณโค้ดที่สร้างโดยมาโครแบบโพรซีเยอร์ (procedural macro) และมาโครแบบประกาศ (declarative macro) โดยแบบแรกมักน่าสนใจมากกว่า

หรือหากคุณต้องการวัดทุกเครตในโปรเจกต์ของคุณ:
```text
RUSTFLAGS="-Zmacro-stats" cargo +nightly build
```
หากต้องการดูโค้ดที่ถูกขยายออกมาเอง คุณสามารถใช้ [cargo-expand]

[cargo-expand]: https://github.com/dtolnay/cargo-expand

ไม่จำเป็นต้องกังวลกับมาโครที่สร้างโค้ดปริมาณน้อย แต่ถ้ามาโครตัวหนึ่งสร้างโค้ดในปริมาณที่เทียบได้กับโค้ดที่เขียนด้วยมือ อาจเป็นไปได้ที่จะเลิกใช้มาโครนั้นทั้งหมด หรือแทนที่ด้วยทางเลือกที่ต้นทุนต่ำกว่า
[**ตัวอย่าง**](https://nnethercote.github.io/2025/06/26/how-much-code-does-that-proc-macro-generate.html).

หรืออีกทางหนึ่ง อาจเป็นไปได้ที่จะดัดแปลงมาโครให้สร้างโค้ดน้อยลง
[**ตัวอย่างที่ 1**](https://github.com/bevyengine/bevy/issues/19873),
[**ตัวอย่างที่ 2**](https://nnethercote.github.io/2025/08/16/speed-wins-when-fuzzing-rust-code-with-derive-arbitrary.html).

## LLVM IR

คอมไพเลอร์ Rust ใช้ [LLVM] เป็นแบ็กเอนด์ การทำงานของ LLVM อาจคิดเป็นส่วนใหญ่ของเวลาในการคอมไพล์ โดยเฉพาะเมื่อฟรอนต์เอนด์ของคอมไพเลอร์ Rust สร้าง [IR] จำนวนมากซึ่งทำให้ LLVM ใช้เวลานานในการเพิ่มประสิทธิภาพ

[LLVM]: https://llvm.org/
[IR]: https://en.wikipedia.org/wiki/Intermediate_representation

ปัญหานี้สามารถวินิจฉัยได้ด้วย [`cargo llvm-lines`] ซึ่งแสดงให้เห็นว่าฟังก์ชัน Rust ใดทำให้เกิดการสร้าง LLVM IR มากที่สุด ฟังก์ชันเจเนอริกมักเป็นตัวการสำคัญที่สุด เพราะมันสามารถถูกอินสแตนซ์ได้หลายสิบหรือแม้กระทั่งหลายร้อยครั้งในโปรแกรมขนาดใหญ่

[`cargo llvm-lines`]: https://github.com/dtolnay/cargo-llvm-lines/

หากฟังก์ชันเจเนอริกทำให้ IR บวมขึ้น มีหลายวิธีแก้ วิธีที่ง่ายที่สุดคือทำให้ฟังก์ชันเล็กลง
[**ตัวอย่างที่ 1**](https://github.com/rust-lang/rust/pull/72166/commits/5a0ac0552e05c079f252482cfcdaab3c4b39d614),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/91246/commits/f3bda74d363a060ade5e5caeb654ba59bfed51a4).

อีกวิธีหนึ่งคือย้ายส่วนที่ไม่ใช่เจเนอริกของฟังก์ชันออกไปเป็นฟังก์ชันแยกที่ไม่ใช่เจเนอริก ซึ่งจะถูกอินสแตนซ์เพียงครั้งเดียว การทำเช่นนี้เป็นไปได้หรือไม่ขึ้นอยู่กับรายละเอียดของฟังก์ชันเจเนอริกนั้น เมื่อเป็นไปได้ ฟังก์ชันที่ไม่ใช่เจเนอริกมักเขียนเป็นฟังก์ชันซ้อนภายในฟังก์ชันเจเนอริกได้อย่างเรียบร้อย ดังที่โค้ดของ
[`std::fs::read`]:
```rust,ignore
pub fn read<P: AsRef<Path>>(path: P) -> io::Result<Vec<u8>> {
    fn inner(path: &Path) -> io::Result<Vec<u8>> {
        let mut file = File::open(path)?;
        let size = file.metadata().map(|m| m.len()).unwrap_or(0);
        let mut bytes = Vec::with_capacity(size as usize);
        io::default_read_to_end(&mut file, &mut bytes)?;
        Ok(bytes)
    }
    inner(path.as_ref())
}
```
[`std::fs::read`]: https://doc.rust-lang.org/std/fs/fn.read.html

[**ตัวอย่าง**](https://github.com/rust-lang/rust/pull/72013/commits/68b75033ad78d88872450a81745cacfc11e58178).

บางครั้งฟังก์ชันอรรถประโยชน์ทั่วไปอย่าง [`Option::map`] และ [`Result::map_err`] ถูกอินสแตนซ์หลายครั้ง การแทนที่ด้วยนิพจน์ `match` ที่ให้ผลเทียบเท่ากันอาจช่วยลดเวลาในการคอมไพล์ได้

[`Option::map`]: https://doc.rust-lang.org/std/option/enum.Option.html#method.map
[`Result::map_err`]: https://doc.rust-lang.org/std/result/enum.Result.html#method.map_err

ผลของการเปลี่ยนแปลงลักษณะนี้ต่อเวลาในการคอมไพล์มักมีน้อย แต่นานๆ ครั้งอาจมีผลมากได้
[**ตัวอย่าง**](https://github.com/servo/servo/issues/26585).

การเปลี่ยนแปลงเช่นนี้ยังอาจลดขนาดไบนารีได้ด้วย

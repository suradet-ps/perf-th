# การตั้งค่าการบิลด์

คุณสามารถเปลี่ยนประสิทธิภาพของโปรแกรม Rust ได้อย่างมากโดยไม่ต้องแก้ไขโค้ด เพียงเปลี่ยนการตั้งค่าการบิลด์ (build configuration) ของมัน โปรแกรม Rust แต่ละโปรแกรมมีการตั้งค่าการบิลด์ที่เป็นไปได้หลายรูปแบบ สิ่งที่เลือกจะส่งผลต่อคุณลักษณะหลายอย่างของโค้ดที่คอมไพล์แล้ว เช่น เวลาในการคอมไพล์ ความเร็วในการทำงาน การใช้หน่วยความจำ ขนาดไบนารี ความสามารถในการดีบัก ความสามารถในการโปรไฟล์ และสถาปัตยกรรมที่โปรแกรมที่คอมไพล์แล้วจะรันได้

ตัวเลือกการตั้งค่าส่วนใหญ่จะปรับปรุงคุณลักษณะหนึ่งหรือหลายอย่าง แลกกับการทำให้คุณลักษณะอื่นแย่ลง ตัวอย่างข้อแลกเปลี่ยนที่พบบ่อยคือการยอมให้เวลาในการคอมไพล์นานขึ้นเพื่อแลกกับความเร็วในการทำงานที่สูงขึ้น ตัวเลือกที่เหมาะสมสำหรับโปรแกรมของคุณขึ้นอยู่กับความต้องการและรายละเอียดเฉพาะของโปรแกรม และตัวเลือกที่เกี่ยวกับประสิทธิภาพ (ซึ่งมีอยู่เกือบทั้งหมด) ควรตรวจสอบยืนยันด้วยการทำเบนช์มาร์ก

การอ่านบทนี้อย่างละเอียดนั้นคุ้มค่า เพื่อให้เข้าใจตัวเลือกการตั้งค่าการบิลด์ทั้งหมด อย่างไรก็ตาม สำหรับผู้ที่ใจร้อนหรือขี้ลืม [`cargo-wizard`] ได้รวบรวมข้อมูลนี้ไว้และช่วยคุณเลือกการตั้งค่าการบิลด์ที่เหมาะสมได้

โปรดทราบว่า Cargo จะดูเฉพาะการตั้งค่าโปรไฟล์ในไฟล์ `Cargo.toml` ที่รากของเวิร์กสเปซเท่านั้น การตั้งค่าโปรไฟล์ที่กำหนดไว้ในดีเพนเดนซีจะถูกละเว้น ดังนั้น ตัวเลือกเหล่านี้จึงเกี่ยวข้องเป็นหลักกับไบนารีเครต (binary crate) ไม่ใช่ไลบรารีเครต (library crate)

[`cargo-wizard`]: https://github.com/Kobzol/cargo-wizard

## บิลด์แบบรีลีส

ตัวเลือกการตั้งค่าการบิลด์ที่สำคัญที่สุดเพียงอย่างเดียวเรียบง่าย แต่[มองข้ามได้ง่าย]: ตรวจสอบให้แน่ใจว่าคุณใช้[บิลด์แบบรีลีส]ไม่ใช่[บิลด์แบบเดฟ]เมื่อต้องการประสิทธิภาพสูง ซึ่งโดยปกติทำได้โดยระบุแฟล็ก `--release` ให้กับ Cargo

[มองข้ามได้ง่าย]: https://users.rust-lang.org/t/why-my-rust-program-is-so-slow/47764/5
[บิลด์แบบรีลีส]: https://doc.rust-lang.org/cargo/reference/profiles.html#release
[บิลด์แบบเดฟ]: https://doc.rust-lang.org/cargo/reference/profiles.html#dev

บิลด์แบบเดฟเป็นค่าเริ่มต้น เหมาะสำหรับการดีบัก แต่ไม่ผ่านการเพิ่มประสิทธิภาพ บิลด์นี้จะถูกสร้างเมื่อคุณรัน `cargo build` หรือ `cargo run` (หรืออีกทางหนึ่ง การรัน `rustc` โดยไม่มีตัวเลือกเพิ่มเติมก็สร้างบิลด์ที่ไม่ผ่านการเพิ่มประสิทธิภาพเช่นกัน)

ลองพิจารณาบรรทัดสุดท้ายของเอาต์พุตจากการรัน `cargo build` ต่อไปนี้
```text
Finished dev [unoptimized + debuginfo] target(s) in 29.80s
```
เอาต์พุตนี้บ่งชี้ว่าได้สร้างบิลด์แบบเดฟขึ้น โค้ดที่คอมไพล์แล้วจะอยู่ในไดเรกทอรี `target/debug/` และ `cargo run` จะรันบิลด์แบบเดฟนี้

ในทางตรงกันข้าม บิลด์แบบรีลีสผ่านการเพิ่มประสิทธิภาพมามากกว่ามาก ตัดแอสเซอร์ชันดีบัก (debug assertion) และการตรวจสอบจำนวนเต็มล้น (integer overflow check) ออก และไม่รวมข้อมูลดีบัก การได้ความเร็วเพิ่มขึ้น 10-100 เท่าเมื่อเทียบกับบิลด์แบบเดฟถือเป็นเรื่องปกติ! บิลด์นี้จะถูกสร้างเมื่อคุณรัน `cargo build --release` หรือ `cargo run --release` (หรืออีกทางหนึ่ง `rustc` มีตัวเลือกหลายอย่างสำหรับบิลด์ที่เพิ่มประสิทธิภาพแล้ว เช่น `-O` และ `-C opt-level`) โดยทั่วไปจะใช้เวลานานกว่าบิลด์แบบเดฟเนื่องจากมีการเพิ่มประสิทธิภาพเพิ่มเติม

ลองพิจารณาบรรทัดสุดท้ายของเอาต์พุตจากการรัน `cargo build --release` ต่อไปนี้
```text
Finished release [optimized] target(s) in 1m 01s
```
เอาต์พุตนี้บ่งชี้ว่าได้สร้างบิลด์แบบรีลีสขึ้น โค้ดที่คอมไพล์แล้วจะอยู่ในไดเรกทอรี `target/release/` และ `cargo run --release` จะรันบิลด์แบบรีลีสนี้

ดู[เอกสารโปรไฟล์ของ Cargo]สำหรับรายละเอียดเพิ่มเติมเกี่ยวกับความแตกต่างระหว่างบิลด์แบบเดฟ (ซึ่งใช้โปรไฟล์ `dev`) และบิลด์แบบรีลีส (ซึ่งใช้โปรไฟล์ `release`)

[เอกสารโปรไฟล์ของ Cargo]: https://doc.rust-lang.org/cargo/reference/profiles.html

ตัวเลือกการตั้งค่าการบิลด์เริ่มต้นที่ใช้ในบิลด์แบบรีลีสให้ความสมดุลที่ดีระหว่างคุณลักษณะที่กล่าวมาข้างต้น เช่น เวลาในการคอมไพล์ ความเร็วในการทำงาน และขนาดไบนารี แต่ยังมีการปรับแต่งที่เป็นไปได้อีกมากมาย ดังที่หัวข้อต่อไปนี้จะอธิบาย

## การเพิ่มความเร็วในการทำงานสูงสุด

ตัวเลือกการตั้งค่าการบิลด์ต่อไปนี้ออกแบบขึ้นเพื่อเพิ่มความเร็วในการทำงานสูงสุดเป็นหลัก บางตัวเลือกอาจลดขนาดไบนารีได้ด้วย

### หน่วยโค้ดเจน

คอมไพเลอร์ Rust แบ่งเครตออกเป็นหลาย[หน่วยโค้ดเจน]เพื่อประมวลผลการคอมไพล์แบบขนาน (และทำให้เร็วขึ้น) อย่างไรก็ตาม การทำเช่นนี้อาจทำให้พลาดการเพิ่มประสิทธิภาพบางอย่างที่ทำได้ คุณอาจเพิ่มความเร็วในการทำงานและลดขนาดไบนารีได้ โดยแลกกับเวลาในการคอมไพล์ที่เพิ่มขึ้น ด้วยการตั้งค่าจำนวนหน่วยเป็นหนึ่ง เพิ่มบรรทัดต่อไปนี้ลงในไฟล์ `Cargo.toml`:
```toml
[profile.release]
codegen-units = 1
```

### การเพิ่มประสิทธิภาพตอนลิงก์

[การเพิ่มประสิทธิภาพตอนลิงก์] (link-time optimization; LTO) เป็นเทคนิคการเพิ่มประสิทธิภาพทั้งโปรแกรมที่สามารถเพิ่มความเร็วในการทำงานได้ 10-20% หรือมากกว่า และลดขนาดไบนารีได้ด้วย โดยแลกกับเวลาในการคอมไพล์ที่แย่ลง ซึ่งมีอยู่หลายรูปแบบ

[การเพิ่มประสิทธิภาพตอนลิงก์]: https://doc.rust-lang.org/cargo/reference/profiles.html#lto

รูปแบบแรกของ LTO คือ *thin local LTO* ซึ่งเป็น LTO รูปแบบน้ำหนักเบา โดยค่าเริ่มต้น คอมไพเลอร์จะใช้รูปแบบนี้กับบิลด์ทุกระดับการเพิ่มประสิทธิภาพที่ไม่ใช่ศูนย์ ซึ่งรวมถึงบิลด์แบบรีลีส หากต้องการเรียกใช้ LTO ระดับนี้อย่างชัดเจน ให้ใส่บรรทัดต่อไปนี้ในไฟล์ `Cargo.toml`:
```toml
[profile.release]
lto = false
```

รูปแบบที่สองของ LTO คือ *thin LTO* ซึ่งเข้มข้นกว่าเล็กน้อย และมีแนวโน้มจะเพิ่มความเร็วในการทำงานและลดขนาดไบนารี พร้อมกับเพิ่มเวลาในการคอมไพล์ ใช้ `lto = "thin"` ใน `Cargo.toml` เพื่อเปิดใช้งาน

รูปแบบที่สามของ LTO คือ *fat LTO* ซึ่งเข้มข้นยิ่งขึ้นไปอีก และอาจเพิ่มประสิทธิภาพและลดขนาดไบนารีได้มากกว่าเดิม (แต่[ไม่เสมอไป]) พร้อมกับเพิ่มเวลาในการบิลด์อีกครั้ง ใช้ `lto = "fat"` ใน `Cargo.toml` เพื่อเปิดใช้งาน

[ไม่เสมอไป]: https://github.com/rust-lang/rust/pull/103453

สุดท้าย คุณสามารถปิด LTO ได้ทั้งหมด ซึ่งมีแนวโน้มจะทำให้ความเร็วในการทำงานแย่ลงและขนาดไบนารีเพิ่มขึ้น แต่จะลดเวลาในการคอมไพล์ลง ใช้ `lto = "off"` ใน `Cargo.toml` สำหรับกรณีนี้ โปรดทราบว่าตัวเลือกนี้แตกต่างจาก `lto = false` ซึ่งตามที่กล่าวข้างต้นจะยังคงเปิด thin local LTO ไว้

### อัลโลเคเตอร์ทางเลือก

คุณสามารถแทนที่อัลโลเคเตอร์ฮีปเริ่มต้น (ของระบบ) ที่โปรแกรม Rust ใช้ ด้วยอัลโลเคเตอร์ทางเลือกได้ ผลลัพธ์ที่แน่นอนจะขึ้นอยู่กับโปรแกรมแต่ละโปรแกรมและอัลโลเคเตอร์ทางเลือกที่เลือก แต่ในทางปฏิบัติพบว่าช่วยเพิ่มความเร็วในการทำงานได้อย่างมากและลดการใช้หน่วยความจำได้อย่างมากเช่นกัน ผลลัพธ์ยังแตกต่างกันไปตามแพลตฟอร์ม เพราะอัลโลเคเตอร์ของระบบแต่ละแพลตฟอร์มมีจุดแข็งและจุดอ่อนของตัวเอง การใช้อัลโลเคเตอร์ทางเลือกยังมีแนวโน้มจะเพิ่มขนาดไบนารีและเวลาในการคอมไพล์ด้วย

#### jemalloc

อัลโลเคเตอร์ทางเลือกยอดนิยมตัวหนึ่งสำหรับ Linux และ Mac คือ [jemalloc] ซึ่งใช้ได้ผ่านเครต [`tikv-jemallocator`] หากต้องการใช้ ให้เพิ่มดีเพนเดนซีลงในไฟล์ `Cargo.toml`:
```toml
[dependencies]
tikv-jemallocator = "0.5"
```
จากนั้นเพิ่มโค้ดต่อไปนี้ลงในโค้ด Rust ของคุณ เช่น ที่ด้านบนของ `src/main.rs`:
```rust,ignore
#[global_allocator]
static GLOBAL: tikv_jemallocator::Jemalloc = tikv_jemallocator::Jemalloc;
```

นอกจากนี้ บน Linux สามารถตั้งค่า jemalloc ให้ใช้[หน่วยความจำแบบ huge page โปร่งใส][THP] (transparent huge pages; THP) ได้ ซึ่งช่วยเพิ่มความเร็วของโปรแกรมได้อีก อาจแลกกับการใช้หน่วยความจำที่สูงขึ้น

[THP]: https://www.kernel.org/doc/html/next/admin-guide/mm/transhuge.html

ทำได้โดยตั้งค่าตัวแปรสภาพแวดล้อม `MALLOC_CONF` (หรืออาจใช้ [`_RJEM_MALLOC_CONF`]) ให้เหมาะสมก่อนบิลด์โปรแกรม ตัวอย่างเช่น:
```bash
MALLOC_CONF="thp:always,metadata_thp:always" cargo build --release
```
ระบบที่รันโปรแกรมที่คอมไพล์แล้วก็ต้องตั้งค่าให้รองรับ THP ด้วย ดู[บทความบล็อกนี้]สำหรับรายละเอียดเพิ่มเติม

[`_RJEM_MALLOC_CONF`]: https://github.com/tikv/jemallocator/issues/65
[บทความบล็อกนี้]: https://kobzol.github.io/rust/rustc/2023/10/21/make-rust-compiler-5percent-faster.html

#### mimalloc

อัลโลเคเตอร์ทางเลือกอีกตัวที่ทำงานได้บนหลายแพลตฟอร์มคือ [mimalloc] ซึ่งใช้ได้ผ่านเครต [`mimalloc`] หากต้องการใช้ ให้เพิ่มดีเพนเดนซีลงในไฟล์ `Cargo.toml`:
```toml
[dependencies]
mimalloc = "0.1"
```
จากนั้นเพิ่มโค้ดต่อไปนี้ลงในโค้ด Rust ของคุณ เช่น ที่ด้านบนของ `src/main.rs`:
```rust,ignore
#[global_allocator]
static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;
```

[jemalloc]: https://github.com/jemalloc/jemalloc
[`tikv-jemallocator`]: https://crates.io/crates/tikv-jemallocator
[ประสิทธิภาพที่ดีขึ้น]: https://github.com/rust-lang/rust/pull/83152

### คำสั่งเฉพาะซีพียู

หากคุณไม่สนใจความเข้ากันได้ของไบนารีกับโปรเซสเซอร์รุ่นเก่า (หรือชนิดอื่น) คุณสามารถสั่งให้คอมไพเลอร์สร้างคำสั่งที่ใหม่ที่สุด (และอาจเร็วที่สุด) ซึ่งเฉพาะกับ[สถาปัตยกรรมซีพียูหนึ่งๆ] เช่น คำสั่ง AVX SIMD สำหรับซีพียู x86-64

[สถาปัตยกรรมซีพียูหนึ่งๆ]: https://doc.rust-lang.org/rustc/codegen-options/index.html#target-cpu

หากต้องการเรียกใช้คำสั่งเหล่านี้จากบรรทัดคำสั่ง ให้ใช้แฟล็ก `-C target-cpu=native` ตัวอย่างเช่น:
```bash
RUSTFLAGS="-C target-cpu=native" cargo build --release
```

หรืออีกทางหนึ่ง หากต้องการเรียกใช้คำสั่งเหล่านี้จากไฟล์ [`config.toml`] (สำหรับหนึ่งโปรเจกต์หรือมากกว่า) ให้เพิ่มบรรทัดต่อไปนี้:
```toml
[build]
rustflags = ["-C", "target-cpu=native"]
```
[`config.toml`]: https://doc.rust-lang.org/cargo/reference/config.html

วิธีนี้อาจเพิ่มความเร็วในการทำงาน โดยเฉพาะอย่างยิ่งหากคอมไพเลอร์พบโอกาสในการทำเวกเตอร์ไรเซชัน (vectorization) ในโค้ดของคุณ

หากคุณไม่แน่ใจว่า `-C target-cpu=native` ทำงานได้อย่างเหมาะสมที่สุดหรือไม่ ให้เปรียบเทียบเอาต์พุตของ `rustc --print cfg` กับ `rustc --print cfg -C target-cpu=native` เพื่อดูว่าฟีเจอร์ของซีพียูถูกตรวจพบอย่างถูกต้องในกรณีหลังหรือไม่ หากไม่ถูกต้อง คุณสามารถใช้ `-C target-feature` เพื่อเจาะจงฟีเจอร์ที่ต้องการได้

### การเพิ่มประสิทธิภาพโดยใช้ข้อมูลโปรไฟล์

การเพิ่มประสิทธิภาพโดยใช้ข้อมูลโปรไฟล์ (profile-guided optimization; PGO) เป็นรูปแบบการคอมไพล์ที่คุณคอมไพล์โปรแกรม รันด้วยข้อมูลตัวอย่างพร้อมกับเก็บข้อมูลการโปรไฟล์ แล้วใช้ข้อมูลการโปรไฟล์นั้นนำทางการคอมไพล์โปรแกรมครั้งที่สอง วิธีนี้อาจเพิ่มความเร็วในการทำงานได้ 10% หรือมากกว่า
[**ตัวอย่างที่ 1**](https://blog.rust-lang.org/inside-rust/2020/11/11/exploring-pgo-for-the-rust-compiler.html),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/96978).

เป็นเทคนิคขั้นสูงที่ต้องใช้ความพยายามในการตั้งค่าพอสมควร แต่คุ้มค่าในบางกรณี ดูรายละเอียดได้ที่[เอกสาร PGO ของ rustc] นอกจากนี้ คำสั่ง [`cargo-pgo`] ยังช่วยให้ใช้ PGO (และ [BOLT] ซึ่งคล้ายกัน) เพื่อเพิ่มประสิทธิภาพไบนารี Rust ได้ง่ายขึ้น

น่าเสียดายที่ PGO ไม่รองรับไบนารีที่โฮสต์บน crates.io และเผยแพร่ผ่าน `cargo install` ซึ่งจำกัดการนำไปใช้

[เอกสาร PGO ของ rustc]: https://doc.rust-lang.org/rustc/profile-guided-optimization.html
[`cargo-pgo`]: https://github.com/Kobzol/cargo-pgo
[BOLT]: https://github.com/llvm/llvm-project/tree/main/bolt

## การลดขนาดไบนารี

ตัวเลือกการตั้งค่าการบิลด์ต่อไปนี้ออกแบบขึ้นเพื่อลดขนาดไบนารีเป็นหลัก ผลกระทบต่อความเร็วในการทำงานนั้นแตกต่างกันไป

### ระดับการเพิ่มประสิทธิภาพ

คุณสามารถขอ[ระดับการเพิ่มประสิทธิภาพ]ที่มุ่งลดขนาดไบนารีได้ โดยเพิ่มบรรทัดต่อไปนี้ลงในไฟล์ `Cargo.toml`:
```toml
[profile.release]
opt-level = "z"
```
[ระดับการเพิ่มประสิทธิภาพ]: https://doc.rust-lang.org/cargo/reference/profiles.html#opt-level

วิธีนี้อาจลดความเร็วในการทำงานลงด้วย

ทางเลือกอีกอย่างคือ `opt-level = "s"` ซึ่งมุ่งลดขนาดไบนารีน้อยลงเล็กน้อย เมื่อเทียบกับ `opt-level = "z"` ตัวเลือกนี้ยอมให้[อินไลน์ได้มากขึ้นเล็กน้อย] และยังทำเวกเตอร์ไรเซชันของลูปได้ด้วย

[อินไลน์ได้มากขึ้นเล็กน้อย]: https://doc.rust-lang.org/rustc/codegen-options/index.html#inline-threshold

### Abort เมื่อเกิด `panic!`

หากคุณไม่จำเป็นต้องคลายสแตกเมื่อเกิดการแพนิก เช่น เพราะโปรแกรมของคุณไม่ได้ใช้ [`catch_unwind`] คุณสามารถสั่งให้คอมไพเลอร์[ยกเลิกทันทีเมื่อเกิดแพนิก]ได้ เมื่อเกิดการแพนิก โปรแกรมของคุณจะยังคงสร้างแบ็กเทรซ

[`catch_unwind`]: https://doc.rust-lang.org/std/panic/fn.catch_unwind.html
[ยกเลิกทันทีเมื่อเกิดแพนิก]: https://doc.rust-lang.org/cargo/reference/profiles.html#panic

วิธีนี้อาจลดขนาดไบนารีและเพิ่มความเร็วในการทำงานเล็กน้อย และอาจลดเวลาในการคอมไพล์ลงเล็กน้อยด้วย เพิ่มบรรทัดต่อไปนี้ลงในไฟล์ `Cargo.toml`:
```toml
[profile.release]
panic = "abort"
```

### การตัดสัญลักษณ์

คุณสามารถสั่งให้คอมไพเลอร์[ตัด][strip]สัญลักษณ์ออกจากบิลด์แบบรีลีสได้ โดยเพิ่มบรรทัดต่อไปนี้ลงใน `Cargo.toml`:
```toml
[profile.release]
strip = "symbols"
```
[strip]: https://doc.rust-lang.org/cargo/reference/profiles.html#strip

[**ตัวอย่าง**](https://github.com/nnethercote/counts/commit/53cab44cd09ff1aa80de70a6dbe1893ff8a41142).

อย่างไรก็ตาม การตัดสัญลักษณ์อาจทำให้โปรแกรมที่คอมไพล์แล้วดีบักและโปรไฟล์ได้ยากขึ้น ตัวอย่างเช่น หากโปรแกรมที่ตัดสัญลักษณ์แล้วเกิดการแพนิก แบ็กเทรซที่ได้อาจมีข้อมูลที่เป็นประโยชน์น้อยกว่าปกติ ผลลัพธ์ที่แน่นอนขึ้นอยู่กับแพลตฟอร์ม

ไม่จำเป็นต้องตัดข้อมูลดีบักออกจากบิลด์แบบรีลีส โดยค่าเริ่มต้น ข้อมูลดีบักจะไม่ถูกสร้างขึ้นสำหรับบิลด์แบบรีลีสในเครื่อง และข้อมูลดีบักของไลบรารีมาตรฐานจะถูกตัดออกโดยอัตโนมัติในบิลด์แบบรีลีส[ตั้งแต่ Rust 1.77]

[ตั้งแต่ Rust 1.77]: https://blog.rust-lang.org/2024/03/21/Rust-1.77.0.html#enable-strip-in-release-profiles-by-default

### แนวคิดอื่นๆ

สำหรับเทคนิคการลดขนาดไบนารีขั้นสูงเพิ่มเติม โปรดดูเอกสารที่ครอบคลุมในที่เก็บ [`min-sized-rust`] ที่ยอดเยี่ยม

[`min-sized-rust`]: https://github.com/johnthagen/min-sized-rust

## การลดเวลาในการคอมไพล์

ตัวเลือกการตั้งค่าการบิลด์ต่อไปนี้ออกแบบขึ้นเพื่อลดเวลาในการคอมไพล์เป็นหลัก

### การลิงก์

ส่วนใหญ่ของเวลาในการคอมไพล์ที่จริงแล้วคือเวลาลิงก์ โดยเฉพาะเมื่อบิลด์โปรแกรมใหม่หลังการเปลี่ยนแปลงเล็กน้อย บนบางแพลตฟอร์มสามารถเลือกตัวลิงก์ที่เร็วกว่าค่าเริ่มต้นได้

ตัวเลือกหนึ่งคือ [lld] ซึ่งใช้ได้บน Linux และ Windows โดย lld เป็นตัวลิงก์เริ่มต้นบน Linux[ตั้งแต่ Rust 1.90] แต่ยังไม่ใช่ค่าเริ่มต้นบน Windows แม้ว่าจะทำงานได้กับกรณีใช้งานส่วนใหญ่

[ตั้งแต่ Rust 1.90]: https://blog.rust-lang.org/2025/09/01/rust-lld-on-1.90.0-stable/

หากต้องการระบุ lld จากบรรทัดคำสั่ง ให้ใช้แฟล็ก `-C link-arg=-fuse-ld=lld` ตัวอย่างเช่น:
```bash
RUSTFLAGS="-C link-arg=-fuse-ld=lld" cargo build --release
```

[lld]: https://lld.llvm.org/

หรืออีกทางหนึ่ง หากต้องการระบุ lld จากไฟล์ [`config.toml`] (สำหรับหนึ่งโปรเจกต์หรือมากกว่า) ให้เพิ่มบรรทัดต่อไปนี้:
```toml
[build]
rustflags = ["-C", "link-arg=-fuse-ld=lld"]
```
[`config.toml`]: https://doc.rust-lang.org/cargo/reference/config.html

มี [GitHub Issue] ที่ติดตามความคืบหน้าการรองรับ lld อย่างเต็มรูปแบบ

[GitHub Issue]: https://github.com/rust-lang/rust/issues/39915#issuecomment-618726211

อีกตัวเลือกหนึ่งคือ [mold] ซึ่งปัจจุบันใช้ได้บน Linux เพียงแทนที่ `lld` ด้วย `mold` ในคำแนะนำข้างต้น mold มักเร็วกว่า lld
[**ตัวอย่าง**](https://davidlattimore.github.io/posts/2024/02/04/speeding-up-the-rust-edit-build-run-cycle.html).
แต่มันใหม่กว่ามากและอาจไม่ทำงานในทุกกรณี

[mold]: https://github.com/rui314/mold

ตัวเลือกสุดท้ายคือ [wild] ซึ่งปัจจุบันใช้ได้เฉพาะบน Linux เท่านั้น อาจเร็วกว่า mold ด้วยซ้ำ แต่ยังไม่สมบูรณ์เท่า

[wild]: https://github.com/davidlattimore/wild

บน Mac ไม่จำเป็นต้องใช้ตัวลิงก์ทางเลือก เพราะตัวลิงก์ของระบบนั้นเร็วอยู่แล้ว

ต่างจากตัวเลือกอื่นๆ ในบทนี้ การเลือกตัวลิงก์อื่นไม่มีข้อแลกเปลี่ยน ตราบใดที่ตัวลิงก์ทำงานถูกต้องกับโปรแกรมของคุณ ซึ่งมักเป็นจริงเว้นแต่คุณกำลังทำสิ่งผิดปกติ ตัวลิงก์ทางเลือกสามารถเร็วขึ้นอย่างมากโดยไม่มีข้อเสียใดๆ

### ปิดการสร้างข้อมูลดีบัก

แม้ว่าบิลด์แบบรีลีสให้ประสิทธิภาพดีที่สุด แต่หลายคนใช้บิลด์แบบเดฟระหว่างพัฒนาเพราะบิลด์เร็วกว่า หากคุณใช้บิลด์แบบเดฟแต่ไม่ค่อยใช้ดีบักเกอร์ ลองพิจารณาปิดข้อมูลดีบักดู ซึ่งช่วยลดเวลาในการบิลด์แบบเดฟได้อย่างมีนัยสำคัญ มากถึง 20-40%
[**ตัวอย่าง**](https://kobzol.github.io/rust/rustc/2025/05/20/disable-debuginfo-to-improve-rust-compile-times.html)

หากต้องการปิดการสร้างข้อมูลดีบัก ให้เพิ่มบรรทัดต่อไปนี้ลงในไฟล์ `Cargo.toml`:
```toml
[profile.dev]
debug = false
```
โปรดทราบว่าการทำเช่นนี้หมายความว่าแบ็กเทรซจะไม่มีข้อมูลหมายเลขบรรทัด หากคุณต้องการเก็บข้อมูลหมายเลขบรรทัดไว้ แต่ไม่ต้องการข้อมูลเต็มรูปแบบสำหรับดีบักเกอร์ คุณสามารถใช้ `debug = "line-tables-only"` แทน ซึ่งยังคงให้ประโยชน์ด้านเวลาในการคอมไพล์เกือบทั้งหมด

### ฟรอนต์เอนด์แบบขนานเชิงทดลอง

หากคุณใช้ Rust เวอร์ชัน nightly คุณสามารถเปิดใช้งาน[ฟรอนต์เอนด์แบบขนาน][parallel front-end]เชิงทดลองได้ ซึ่งอาจลดเวลาในการคอมไพล์ โดยแลกกับการใช้หน่วยความจำระหว่างคอมไพล์ที่สูงขึ้น แต่จะไม่ส่งผลต่อคุณภาพของโค้ดที่สร้างขึ้น

[parallel front-end]: https://blog.rust-lang.org/2023/11/09/parallel-rustc.html

ทำได้โดยเพิ่ม `-Zthreads=N` ลงใน RUSTFLAGS ตัวอย่างเช่น:
```bash
RUSTFLAGS="-Zthreads=8" cargo build --release
```

หรืออีกทางหนึ่ง หากต้องการเปิดใช้งานฟรอนต์เอนด์แบบขนานจากไฟล์ [`config.toml`] (สำหรับหนึ่งโปรเจกต์หรือมากกว่า) ให้เพิ่มบรรทัดต่อไปนี้:
```toml
[build]
rustflags = ["-Z", "threads=8"]
```
[`config.toml`]: https://doc.rust-lang.org/cargo/reference/config.html

สามารถใช้ค่าอื่นนอกเหนือจาก `8` ได้ แต่ค่านี้มักให้ผลลัพธ์ที่ดีที่สุด

ในกรณีที่ดีที่สุด ฟรอนต์เอนด์แบบขนานเชิงทดลองช่วยลดเวลาในการคอมไพล์ได้ถึง 50% แต่ผลลัพธ์แตกต่างกันมากและขึ้นอยู่กับลักษณะของโค้ดและการตั้งค่าการบิลด์ และบางโปรแกรมก็ไม่ได้รับประโยชน์ด้านเวลาในการคอมไพล์เลย

### แบ็กเอนด์โค้ดเจน Cranelift

หากคุณใช้ Rust เวอร์ชัน nightly คุณสามารถเปิดใช้แบ็กเอนด์โค้ดเจน Cranelift บน[บางแพลตฟอร์ม][some platforms]ได้ ซึ่งอาจลดเวลาในการคอมไพล์โดยแลกกับคุณภาพของโค้ดที่สร้างขึ้นที่ต่ำลง จึงแนะนำให้ใช้กับบิลด์แบบเดฟมากกว่าบิลด์แบบรีลีส

ก่อนอื่น ติดตั้งแบ็กเอนด์ด้วยคำสั่ง `rustup` นี้:
```bash
rustup component add rustc-codegen-cranelift-preview --toolchain nightly
```

หากต้องการเลือก Cranelift จากบรรทัดคำสั่ง ให้ใช้แฟล็ก `-Zcodegen-backend=cranelift` ตัวอย่างเช่น:
```bash
RUSTFLAGS="-Zcodegen-backend=cranelift" cargo +nightly build
```

หรืออีกทางหนึ่ง หากต้องการระบุ Cranelift จากไฟล์ [`config.toml`] (สำหรับหนึ่งโปรเจกต์หรือมากกว่า) ให้เพิ่มบรรทัดต่อไปนี้:
```toml
[unstable]
codegen-backend = true

[profile.dev]
codegen-backend = "cranelift"
```
[`config.toml`]: https://doc.rust-lang.org/cargo/reference/config.html

สำหรับข้อมูลเพิ่มเติม ดู[เอกสาร Cranelift]

[some platforms]: https://github.com/rust-lang/rustc_codegen_cranelift#platform-support
[เอกสาร Cranelift]: https://github.com/rust-lang/rustc_codegen_cranelift

## โปรไฟล์แบบกำหนดเอง

นอกเหนือจากโปรไฟล์ `dev` และ `release` แล้ว Cargo ยังรองรับ[โปรไฟล์แบบกำหนดเอง]ด้วย ตัวอย่างเช่น อาจมีประโยชน์หากสร้างโปรไฟล์กำหนดเองที่อยู่กึ่งกลางระหว่าง `dev` และ `release` หากคุณรู้สึกว่าความเร็วในการทำงานของบิลด์แบบเดฟไม่เพียงพอ และเวลาในการคอมไพล์ของบิลด์แบบรีลีสช้าเกินไปสำหรับการพัฒนาประจำวัน

[โปรไฟล์แบบกำหนดเอง]: https://doc.rust-lang.org/cargo/reference/profiles.html#custom-profiles

## สรุป

มีการเลือกมากมายที่ต้องตัดสินใจเมื่อพูดถึงการตั้งค่าการบิลด์ ประเด็นต่อไปนี้สรุปข้อมูลข้างต้นออกมาเป็นคำแนะนำ

- หากต้องการเพิ่มความเร็วในการทำงานสูงสุด ลองพิจารณาทั้งหมดต่อไปนี้:
  `codegen-units = 1`, `lto = "fat"`, อัลโลเคเตอร์ทางเลือก และ `panic =
  "abort"`.
- หากต้องการลดขนาดไบนารี ลองพิจารณา `opt-level = "z"`,
  `codegen-units = 1`, `lto = "fat"`, `panic = "abort"` และ `strip =
  "symbols"`.
- ในทั้งสองกรณี ลองพิจารณา `-C target-cpu=native` หากไม่จำเป็นต้องรองรับ
  สถาปัตยกรรมหลากหลาย และ `cargo-pgo` หากใช้ได้กับช่องทางเผยแพร่ของคุณ
- ใช้ตัวลิงก์ที่เร็วกว่าเสมอหากคุณอยู่บนแพลตฟอร์มที่รองรับ เพราะไม่มีข้อเสียใดๆ
  จากการทำเช่นนั้น
- ใช้ `cargo-wizard` หากต้องการความช่วยเหลือเพิ่มเติมในการตัดสินใจเหล่านี้
- ทำเบนช์มาร์กทุกการเปลี่ยนแปลง ทีละอย่าง เพื่อให้แน่ใจว่ามันให้ผลตามที่คาดหวัง

สุดท้าย [issue นี้] ติดตามวิวัฒนาการของการตั้งค่าการบิลด์ของคอมไพเลอร์ Rust เอง ระบบบิลด์ของคอมไพเลอร์ Rust นั้นแปลกกว่าและซับซ้อนกว่าระบบบิลด์ของโปรแกรม Rust ส่วนใหญ่ อย่างไรก็ตาม issue นี้อาจให้ความรู้ในการแสดงให้เห็นว่าตัวเลือกการตั้งค่าการบิลด์สามารถนำไปใช้กับโปรแกรมขนาดใหญ่ได้อย่างไร

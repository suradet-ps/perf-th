# การตั้งค่าการบิลด์

คุณสามารถยกระดับประสิทธิภาพของโปรแกรม Rust ได้อย่างมหาศาลโดยไม่ต้องแตะต้องโค้ดแม้แต่บรรทัดเดียว เพียงแค่ปรับเปลี่ยนการตั้งค่าการบิลด์ (build configuration) เท่านั้น ในแต่ละโปรแกรม Rust มีตัวเลือกการตั้งค่าบิลด์ที่หลากหลาย ซึ่งสิ่งที่คุณเลือกจะส่งผลต่อคุณลักษณะหลายด้านของโค้ดที่คอมไพล์ออกมา ไม่ว่าจะเป็นเวลาที่ใช้ในการคอมไพล์ ความเร็วในการทำงาน การใช้หน่วยความจำ ขนาดของไฟล์ไบนารี ความสะดวกในการดีบักและโปรไฟล์ ตลอดจนสถาปัตยกรรมของซีพียูที่โปรแกรมสามารถรันได้

ตัวเลือกการตั้งค่าส่วนใหญ่จะช่วยพัฒนาคุณลักษณะด้านหนึ่งหรือหลายด้าน โดยต้องแลกมาด้วยการทำให้ด้านอื่นๆ แย่ลง (trade-off) เช่น ตัวอย่างที่พบบ่อยคือการยอมให้คอมไพล์ช้าลง เพื่อแลกกับความเร็วในการทำงานตอนรันที่สูงขึ้น การเลือกค่าที่เหมาะสมจึงขึ้นอยู่กับความต้องการและลักษณะเฉพาะของโปรแกรมของคุณ และเนื่องจากการตั้งค่าเกือบทั้งหมดมีผลต่อประสิทธิภาพ จึงควรตรวจสอบยืนยันผลลัพธ์ด้วยการทำเบนช์มาร์กเสมอ

ขอแนะนำให้อ่านบทนี้อย่างละเอียดเพื่อทำความเข้าใจตัวเลือกการตั้งค่าการบิลด์ทั้งหมด แต่สำหรับใครที่ต้องการความสะดวกรวดเร็วหรือไม่อยากจำรายละเอียดปลีกย่อย เครื่องมือ [`cargo-wizard`] ได้รวบรวมข้อมูลเหล่านี้ไว้และสามารถช่วยคุณเลือกการตั้งค่าการบิลด์ที่เหมาะสมได้โดยอัตโนมัติ

โปรดจำไว้ว่า Cargo จะอ่านการตั้งค่าโปรไฟล์จากไฟล์ `Cargo.toml` ที่อยู่ ณ โฟลเดอร์รากของเวิร์กสเปซเท่านั้น โดยจะละเว้นการตั้งค่าโปรไฟล์ที่ระบุไว้ในบรรดาดีเพนเดนซีภายนอก ดังนั้น ตัวเลือกเหล่านี้จึงมีผลกับไบนารีเครต (binary crate) เป็นหลัก ไม่ใช่ไลบรารีเครต (library crate)

[`cargo-wizard`]: https://github.com/Kobzol/cargo-wizard

## บิลด์แบบรีลีส

สิ่งสำคัญที่สุดเพียงเรื่องเดียวในการตั้งค่าบิลด์ ซึ่งฟังดูเรียบง่ายแต่กลับ[มองข้ามได้ง่าย]: ตรวจสอบให้แน่ใจว่าคุณใช้[บิลด์แบบรีลีส] ไม่ใช่[บิลด์แบบเดฟ] เมื่อต้องการประสิทธิภาพสูง ซึ่งโดยปกติทำได้โดยระบุแฟล็ก `--release` ให้กับ Cargo

[มองข้ามได้ง่าย]: https://users.rust-lang.org/t/why-my-rust-program-is-so-slow/47764/5
[บิลด์แบบรีลีส]: https://doc.rust-lang.org/cargo/reference/profiles.html#release
[บิลด์แบบเดฟ]: https://doc.rust-lang.org/cargo/reference/profiles.html#dev

บิลด์แบบเดฟเป็นค่าเริ่มต้น เหมาะสำหรับการดีบัก แต่ยังไม่ผ่านการเพิ่มประสิทธิภาพใดๆ บิลด์นี้จะถูกสร้างขึ้นเมื่อคุณรันคำสั่ง `cargo build` หรือ `cargo run` (หรือหากรันคำสั่ง `rustc` โดยตรงโดยไม่ใส่ตัวเลือกเพิ่มเติม ก็จะได้บิลด์ที่ไม่ได้ optimize เช่นกัน)

ลองพิจารณาบรรทัดสุดท้ายของเอาต์พุตจากการรัน `cargo build` ต่อไปนี้
```text
Finished dev [unoptimized + debuginfo] target(s) in 29.80s
```
เอาต์พุตนี้บ่งชี้ว่าได้สร้างบิลด์แบบเดฟขึ้น โดยโค้ดที่คอมไพล์แล้วจะถูกจัดเก็บไว้ในโฟลเดอร์ `target/debug/` และคำสั่ง `cargo run` จะนำบิลด์แบบเดฟนี้ไปรัน

ในทางตรงกันข้าม บิลด์แบบรีลีสจะผ่านการเพิ่มประสิทธิภาพมาอย่างเข้มข้น โดยจะตัด debug assertions และการตรวจสอบจำนวนเต็มล้น (integer overflow checks) ออก รวมถึงไม่รวมข้อมูลดีบัก คุณจึงอาจพบว่าโปรแกรมทำงานเร็วขึ้นถึง 10–100 เท่าเมื่อเทียบกับบิลด์แบบเดฟ ซึ่งถือเป็นเรื่องปกติอย่างยิ่ง! บิลด์นี้จะถูกสร้างขึ้นเมื่อคุณรัน `cargo build --release` หรือ `cargo run --release` (หรือหากใช้ `rustc` ก็มีตัวเลือกหลายตัวสำหรับบิลด์ที่เพิ่มประสิทธิภาพแล้ว เช่น `-O` และ `-C opt-level`) โดยทั่วไปจะใช้เวลานานกว่าบิลด์แบบเดฟเนื่องจากคอมไพเลอร์ต้องวิเคราะห์และ optimize เพิ่มเติม

ลองพิจารณาบรรทัดสุดท้ายของเอาต์พุตจากการรัน `cargo build --release` ต่อไปนี้
```text
Finished release [optimized] target(s) in 1m 01s
```
เอาต์พุตนี้บ่งชี้ว่าได้สร้างบิลด์แบบรีลีสขึ้น โดยโค้ดที่คอมไพล์แล้วจะอยู่ในโฟลเดอร์ `target/release/` และคำสั่ง `cargo run --release` จะนำบิลด์แบบรีลีสนี้ไปรัน

ดูรายละเอียดเพิ่มเติมเกี่ยวกับความแตกต่างระหว่างบิลด์แบบเดฟ (ซึ่งใช้โปรไฟล์ `dev`) และบิลด์แบบรีลีส (ซึ่งใช้โปรไฟล์ `release`) ได้ที่ [เอกสารโปรไฟล์ของ Cargo]

[เอกสารโปรไฟล์ของ Cargo]: https://doc.rust-lang.org/cargo/reference/profiles.html

การตั้งค่าเริ่มต้นของบิลด์แบบรีลีสนั้นให้จุดสมดุลที่ดีระหว่างคุณลักษณะต่างๆ ไม่ว่าจะเป็นเวลาในการคอมไพล์ ความเร็วในการทำงาน และขนาดไฟล์ไบนารี แต่ยังมีการปรับแต่งที่เป็นไปได้อีกมากมาย ดังที่หัวข้อต่อไปนี้จะอธิบาย

## การเพิ่มความเร็วในการทำงานสูงสุด

ตัวเลือกการตั้งค่าการบิลด์ต่อไปนี้มุ่งเน้นการเพิ่มความเร็วในการทำงานตอนรันเป็นหลัก ซึ่งบางตัวเลือกอาจช่วยลดขนาดไฟล์ไบนารีลงได้ด้วย

### หน่วยโค้ดเจน

คอมไพเลอร์ Rust จะแบ่งเครตออกเป็นหลาย [หน่วยสร้างโค้ด][หน่วยโค้ดเจน] (codegen units) เพื่อแยกประมวลผลการคอมไพล์แบบขนาน ซึ่งช่วยให้คอมไพล์เสร็จเร็วขึ้น อย่างไรก็ตาม การแยกส่วนเช่นนี้อาจทำให้คอมไพเลอร์พลาดโอกาสในการ optimize ข้ามหน่วยไป คุณสามารถเพิ่มความเร็วในการทำงานและช่วยลดขนาดไบนารีลงได้ โดยแลกกับเวลาคอมไพล์ที่นานขึ้น ด้วยการกำหนดจำนวนหน่วยสร้างโค้ดให้เหลือเพียง 1 หน่วย โดยเพิ่มบรรทัดต่อไปนี้ลงในไฟล์ `Cargo.toml`:
```toml
[profile.release]
codegen-units = 1
```

### การเพิ่มประสิทธิภาพตอนลิงก์

[การเพิ่มประสิทธิภาพในขั้นตอนลิงก์][การเพิ่มประสิทธิภาพตอนลิงก์] (Link-Time Optimization; LTO) เป็นเทคนิคการ optimize ทั้งโปรแกรมแบบองค์รวม (whole-program optimization) ซึ่งช่วยเพิ่มความเร็วในการทำงานได้ถึง 10–20% หรือมากกว่านั้น ทั้งยังช่วยลดขนาดไฟล์ไบนารีลงได้ โดยแลกกับเวลาในการคอมไพล์ที่เพิ่มขึ้น ซึ่ง LTO มีให้เลือกใช้หลายระดับ:

[การเพิ่มประสิทธิภาพตอนลิงก์]: https://doc.rust-lang.org/cargo/reference/profiles.html#lto

รูปแบบแรกคือ *thin local LTO* ซึ่งเป็น LTO รูปแบบน้ำหนักเบา โดยค่าเริ่มต้น คอมไพเลอร์จะเปิดใช้รูปแบบนี้กับทุกบิลด์ที่มีระดับการ optimize ไม่ใช่ศูนย์ (รวมถึงบิลด์แบบรีลีสอยู่แล้ว) หากต้องการระบุ LTO ระดับนี้อย่างชัดเจน ให้ใส่บรรทัดต่อไปนี้ในไฟล์ `Cargo.toml`:
```toml
[profile.release]
lto = false
```

รูปแบบที่สองคือ *thin LTO* ซึ่งเข้มข้นขึ้น มีแนวโน้มช่วยเพิ่มความเร็วและลดขนาดไบนารี โดยแลกกับเวลาในการคอมไพล์ที่เพิ่มขึ้น กำหนดได้โดยใส่ `lto = "thin"` ใน `Cargo.toml`

รูปแบบที่สามคือ *fat LTO* ซึ่งเป็นการ optimize ที่เข้มข้นที่สุด ช่วยรีดประสิทธิภาพและลดขนาดไบนารีได้มากยิ่งขึ้น (แต่[ไม่เสมอไป][ไม่เสมอไป]) โดยแลกกับเวลาบิลด์ที่นานที่สุด กำหนดได้โดยใส่ `lto = "fat"` ใน `Cargo.toml`

[ไม่เสมอไป]: https://github.com/rust-lang/rust/pull/103453

และสุดท้าย คุณสามารถสั่งปิด LTO ทั้งหมดได้ด้วย `lto = "off"` ซึ่งมีแนวโน้มทำให้ความเร็วในการทำงานลดลงและขนาดไบนารีใหญ่ขึ้น แต่จะช่วยลดเวลาในการคอมไพล์ลงอย่างเห็นได้ชัด (โปรดทราบว่าตัวเลือกนี้แตกต่างจาก `lto = false` ซึ่งยังคงเปิด thin local LTO ไว้อยู่)

### อัลโลเคเตอร์ทางเลือก

คุณสามารถเปลี่ยนตัวจัดสรรหน่วยความจำบนฮีป (heap allocator) เริ่มต้นของระบบที่โปรแกรม Rust ใช้งาน ไปเป็นอัลโลเคเตอร์ทางเลือกอื่นได้ ผลลัพธ์ที่ได้จะขึ้นอยู่กับลักษณะเฉพาะของแต่ละโปรแกรมและตัวอัลโลเคเตอร์ที่เลือก แต่ในทางปฏิบัติพบว่ามักช่วยเพิ่มความเร็วในการทำงานและลดการใช้หน่วยความจำลงได้อย่างมีนัยสำคัญ นอกจากนี้ ผลลัพธ์ยังขึ้นอยู่กับระบบปฏิบัติการด้วย เนื่องจาก allocator เริ่มต้นของแต่ละแพลตฟอร์มมีจุดเด่นและจุดด้อยต่างกัน ทั้งนี้ การใช้อัลโลเคเตอร์ภายนอกอาจทำให้ขนาดไฟล์ไบนารีและเวลาในการคอมไพล์เพิ่มขึ้นเล็กน้อย

#### jemalloc

อัลโลเคเตอร์ทางเลือกยอดนิยมสำหรับ Linux และ macOS คือ [jemalloc] ซึ่งเรียกใช้ได้ผ่านเครต [`tikv-jemallocator`] หากต้องการใช้งาน ให้เพิ่มดีเพนเดนซีลงในไฟล์ `Cargo.toml`:
```toml
[dependencies]
tikv-jemallocator = "0.5"
```
จากนั้นเพิ่มโค้ดต่อไปนี้ลงในโค้ด Rust ของคุณ เช่น ที่ด้านบนสุดของไฟล์ `src/main.rs`:
```rust,ignore
#[global_allocator]
static GLOBAL: tikv_jemallocator::Jemalloc = tikv_jemallocator::Jemalloc;
```

นอกจากนี้ บน Linux ยังสามารถกำหนดค่าให้ jemalloc ใช้งาน [Transparent Huge Pages (THP)][THP] ซึ่งช่วยเพิ่มความเร็วของโปรแกรมขึ้นไปได้อีก โดยอาจแลกกับการใช้หน่วยความจำที่สูงขึ้นเล็กน้อย

[THP]: https://www.kernel.org/doc/html/next/admin-guide/mm/transhuge.html

ทำได้โดยตั้งค่าตัวแปรสภาพแวดล้อม `MALLOC_CONF` (หรืออาจใช้ [`_RJEM_MALLOC_CONF`]) ให้เหมาะสมก่อนคอมไพล์โปรแกรม ตัวอย่างเช่น:
```bash
MALLOC_CONF="thp:always,metadata_thp:always" cargo build --release
```
ทั้งนี้ ระบบปลายทางที่จะรันโปรแกรมก็ต้องเปิดใช้งาน THP ด้วยเช่นกัน ดูรายละเอียดเพิ่มเติมได้ที่ [บทความบล็อกนี้]

[`_RJEM_MALLOC_CONF`]: https://github.com/tikv/jemallocator/issues/65
[บทความบล็อกนี้]: https://kobzol.github.io/rust/rustc/2023/10/21/make-rust-compiler-5percent-faster.html

#### mimalloc

อัลโลเคเตอร์ทางเลือกประสิทธิภาพสูงอีกตัวที่ทำงานได้บนหลากหลายแพลตฟอร์มคือ [mimalloc] ซึ่งเรียกใช้ได้ผ่านเครต [`mimalloc`] หากต้องการใช้งาน ให้เพิ่มดีเพนเดนซีลงในไฟล์ `Cargo.toml`:
```toml
[dependencies]
mimalloc = "0.1"
```
จากนั้นเพิ่มโค้ดต่อไปนี้ลงในโค้ด Rust ของคุณ เช่น ที่ด้านบนสุดของไฟล์ `src/main.rs`:
```rust,ignore
#[global_allocator]
static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;
```

[ประสิทธิภาพที่ดีขึ้น]: https://github.com/rust-lang/rust/pull/83152

### คำสั่งเฉพาะซีพียู

หากคุณไม่จำเป็นต้องกังวลเรื่องความเข้ากันได้ของไบนารีกับซีพียูรุ่นเก่าหรือชนิดอื่น คุณสามารถสั่งให้คอมไพเลอร์สร้างชุดคำสั่งที่ใหม่ที่สุดและเร็วที่สุดสำหรับ [สถาปัตยกรรมซีพียูเครื่องปัจจุบันโดยเฉพาะ][สถาปัตยกรรมซีพียูหนึ่งๆ] เช่น การเปิดใช้ชุดคำสั่ง AVX SIMD บนซีพียู x86-64

[สถาปัตยกรรมซีพียูหนึ่งๆ]: https://doc.rust-lang.org/rustc/codegen-options/index.html#target-cpu

หากต้องการสั่งผ่านคอมมานด์ไลน์ ให้ระบุแฟล็ก `-C target-cpu=native` ตัวอย่างเช่น:
```bash
RUSTFLAGS="-C target-cpu=native" cargo build --release
```

หรือหากต้องการกำหนดไว้ถาวรในไฟล์ [`config.toml`] (สำหรับโปรเจกต์เดียวหรือทั้งเวิร์กสเปซ) ให้เพิ่มบรรทัดต่อไปนี้:
```toml
[build]
rustflags = ["-C", "target-cpu=native"]
```
[`config.toml`]: https://doc.rust-lang.org/cargo/reference/config.html

วิธีนี้อาจช่วยเพิ่มความเร็วในการทำงานได้อย่างเห็นได้ชัด โดยเฉพาะในจุดที่คอมไพเลอร์พบโอกาสแปลงลูปให้ทำงานแบบขนานด้วยคำสั่งเวกเตอร์ (vectorization)

หากไม่แน่ใจว่า `-C target-cpu=native` ตรวจพบฟีเจอร์ของซีพียูได้เหมาะสมที่สุดหรือไม่ ให้ลองเปรียบเทียบผลลัพธ์ระหว่าง `rustc --print cfg` กับ `rustc --print cfg -C target-cpu=native` เพื่อดูว่าฟีเจอร์ของซีพียูถูกตรวจพบอย่างครบถ้วนหรือไม่ หากยังไม่ครบ คุณสามารถใช้ `-C target-feature` เพื่อเจาะจงฟีเจอร์ที่ต้องการได้โดยตรง

### การเพิ่มประสิทธิภาพโดยใช้ข้อมูลโปรไฟล์

การเพิ่มประสิทธิภาพโดยอิงข้อมูลโปรไฟล์ (Profile-Guided Optimization; PGO) เป็นกระบวนการคอมไพล์ที่คุณบิลด์โปรแกรมขึ้นมา รันโปรแกรมด้วยข้อมูลตัวอย่างพร้อมกับเก็บข้อมูลการโปรไฟล์ จากนั้นนำข้อมูลสถิติที่ได้ไปป้อนให้คอมไพเลอร์ใช้ตัดสินใจ optimize ในการคอมไพล์โปรแกรมรอบที่สอง ซึ่งวิธีนี้อาจเพิ่มความเร็วในการทำงานได้ถึง 10% หรือมากกว่านั้นเลยทีเดียว
[**ตัวอย่างที่ 1**](https://blog.rust-lang.org/inside-rust/2020/11/11/exploring-pgo-for-the-rust-compiler.html),
[**ตัวอย่างที่ 2**](https://github.com/rust-lang/rust/pull/96978).

เทคนิคนี้เป็นขั้นสูงที่ต้องตั้งค่ากระบวนการหลายขั้นตอน แต่คุ้มค่าอย่างยิ่งในกรณีที่ต้องการรีดประสิทธิภาพสูงสุด ดูรายละเอียดได้ที่ [เอกสาร PGO ของ rustc] นอกจากนี้ เครื่องมือ [`cargo-pgo`] ยังช่วยให้การทำ PGO (รวมถึง [BOLT] ซึ่งเป็นเทคนิคที่คล้ายกัน) ทำได้สะดวกยิ่งขึ้น

อย่างไรก็ตาม PGO ยังไม่รองรับกับไบนารีที่เผยแพร่ผ่าน `cargo install` บน crates.io จึงอาจมีข้อจำกัดในการนำไปใช้งานสำหรับบางกรณี

[เอกสาร PGO ของ rustc]: https://doc.rust-lang.org/rustc/profile-guided-optimization.html
[`cargo-pgo`]: https://github.com/Kobzol/cargo-pgo
[BOLT]: https://github.com/llvm/llvm-project/tree/main/bolt

## การลดขนาดไบนารี

ตัวเลือกการตั้งค่าการบิลด์ต่อไปนี้ออกแบบขึ้นเพื่อมุ่งลดขนาดไฟล์ไบนารีเป็นหลัก โดยผลกระทบต่อความเร็วในการทำงานอาจแตกต่างกันไปในแต่ละโปรแกรม

### ระดับการเพิ่มประสิทธิภาพ

คุณสามารถกำหนด [ระดับการเพิ่มประสิทธิภาพ][ระดับการเพิ่มประสิทธิภาพ] ที่มุ่งเน้นการลดขนาดไบนารีได้ โดยเพิ่มบรรทัดต่อไปนี้ลงในไฟล์ `Cargo.toml`:
```toml
[profile.release]
opt-level = "z"
```
[ระดับการเพิ่มประสิทธิภาพ]: https://doc.rust-lang.org/cargo/reference/profiles.html#opt-level

การตั้งค่านี้อาจส่งผลให้โปรแกรมทำงานช้าลงบ้าง

อีกหนึ่งทางเลือกคือ `opt-level = "s"` ซึ่งมุ่งลดขนาดไบนารีในระดับที่ผ่อนปรนลงมาเล็กน้อย โดยเมื่อเทียบกับ `opt-level = "z"` ตัวเลือกนี้จะยอมให้มี [การอินไลน์ฟังก์ชันได้มากกว่าเล็กน้อย][อินไลน์ได้มากขึ้นเล็กน้อย] รวมถึงยังคงเปิดการทำ loop vectorization ไว้อยู่

[อินไลน์ได้มากขึ้นเล็กน้อย]: https://doc.rust-lang.org/rustc/codegen-options/index.html#inline-threshold

### Abort เมื่อเกิด `panic!`

หากโปรแกรมของคุณไม่จำเป็นต้องมีกระบวนการคลายสแตก (unwinding) เมื่อเกิดแพนิก เช่น โปรแกรมไม่ได้ใช้ฟังก์ชัน [`catch_unwind`] คุณสามารถสั่งให้คอมไพเลอร์ [ยกเลิกการทำงานทันทีเมื่อเกิดแพนิก][ยกเลิกทันทีเมื่อเกิดแพนิก] ได้ ซึ่งเมื่อเกิด panic โปรแกรมจะยังคงแสดงแบ็กเทรซตามปกติ

[`catch_unwind`]: https://doc.rust-lang.org/std/panic/fn.catch_unwind.html
[ยกเลิกทันทีเมื่อเกิดแพนิก]: https://doc.rust-lang.org/cargo/reference/profiles.html#panic

วิธีนี้อาจช่วยลดขนาดไบนารี เพิ่มความเร็วในการทำงานเล็กน้อย และอาจลดเวลาในการคอมไพล์ลงได้ด้วย เพียงเพิ่มบรรทัดต่อไปนี้ลงในไฟล์ `Cargo.toml`:
```toml
[profile.release]
panic = "abort"
```

### การตัดสัญลักษณ์

คุณสามารถสั่งให้คอมไพเลอร์ [ตัดสัญลักษณ์ (strip symbols)][strip] ออกจากบิลด์แบบรีลีสได้ โดยเพิ่มบรรทัดต่อไปนี้ลงใน `Cargo.toml`:
```toml
[profile.release]
strip = "symbols"
```
[strip]: https://doc.rust-lang.org/cargo/reference/profiles.html#strip

[**ตัวอย่าง**](https://github.com/nnethercote/counts/commit/53cab44cd09ff1aa80de70a6dbe1893ff8a41142).

อย่างไรก็ตาม การตัดสัญลักษณ์ทิ้งอาจทำให้โปรแกรมที่คอมไพล์แล้วดีบักและโปรไฟล์ได้ยากขึ้น ตัวอย่างเช่น หากเกิด panic ขึ้นในโปรแกรม แบ็กเทรซที่ได้อาจแสดงข้อมูลที่เป็นประโยชน์น้อยกว่าปกติ ทั้งนี้ผลลัพธ์ที่แน่นอนจะขึ้นอยู่กับแพลตฟอร์ม

คุณไม่จำเป็นต้องกังวลเรื่องการตัดข้อมูลดีบักออกจากบิลด์แบบรีลีสด้วยตนเอง เพราะโดยค่าเริ่มต้น ข้อมูลดีบักจะไม่ถูกสร้างขึ้นในบิลด์แบบรีลีสอยู่แล้ว และข้อมูลดีบักของ Standard Library ก็จะถูกตัดออกโดยอัตโนมัติในบิลด์แบบรีลีส [ตั้งแต่ Rust 1.77][ตั้งแต่ Rust 1.77] เป็นต้นมา

[ตั้งแต่ Rust 1.77]: https://blog.rust-lang.org/2024/03/21/Rust-1.77.0.html#enable-strip-in-release-profiles-by-default

### แนวคิดอื่นๆ

สำหรับเทคนิคการลดขนาดไบนารีขั้นสูงเพิ่มเติม ขอแนะนำให้อ่านคู่มือฉบับสมบูรณ์ในคลังโค้ด [`min-sized-rust`] ซึ่งรวบรวมเทคนิคไว้ได้อย่างยอดเยี่ยม

[`min-sized-rust`]: https://github.com/johnthagen/min-sized-rust

## การลดเวลาในการคอมไพล์

ตัวเลือกการตั้งค่าการบิลด์ต่อไปนี้ ได้รับการออกแบบขึ้นมาเพื่อช่วยลดเวลาในการคอมไพล์เป็นหลัก

### การลิงก์

เวลาส่วนใหญ่ในการคอมไพล์ แท้จริงแล้วคือเวลาในการลิงก์ (linking time) โดยเฉพาะเมื่อต้องคอมไพล์โปรแกรมใหม่หลังจากแก้ไขโค้ดเพียงเล็กน้อย ซึ่งบนบางแพลตฟอร์ม เราสามารถเปลี่ยนไปใช้ linker ที่ทำงานเร็วกว่าค่าเริ่มต้นได้

ตัวเลือกแรกคือ [lld] ซึ่งใช้งานได้ทั้งบน Linux และ Windows โดย lld ถูกตั้งให้เป็น linker เริ่มต้นบน Linux [ตั้งแต่ Rust 1.90] ส่วนบน Windows แม้จะยังไม่ใช่ค่าเริ่มต้น แต่ก็ทำงานได้ดีกับกรณีการใช้งานส่วนใหญ่

[ตั้งแต่ Rust 1.90]: https://blog.rust-lang.org/2025/09/01/rust-lld-on-1.90.0-stable/

หากต้องการระบุให้ใช้ lld ผ่านคอมมานด์ไลน์ ให้ส่งแฟล็ก `-C link-arg=-fuse-ld=lld` ตัวอย่างเช่น:
```bash
RUSTFLAGS="-C link-arg=-fuse-ld=lld" cargo build --release
```

[lld]: https://lld.llvm.org/

หรืออีกทางหนึ่ง หากต้องการตั้งค่า lld ผ่านไฟล์ [`config.toml`] (เพื่อใช้กับโปรเจกต์เดียวหรือหลายโปรเจกต์) ให้เพิ่มการตั้งค่าดังนี้:
```toml
[build]
rustflags = ["-C", "link-arg=-fuse-ld=lld"]
```
[`config.toml`]: https://doc.rust-lang.org/cargo/reference/config.html

สามารถติดตามความคืบหน้าเรื่องการรองรับ lld อย่างเต็มรูปแบบได้ที่ [GitHub Issue]

[GitHub Issue]: https://github.com/rust-lang/rust/issues/39915#issuecomment-618726211

อีกตัวเลือกหนึ่งคือ [mold] ซึ่งปัจจุบันใช้งานได้บน Linux เพียงเปลี่ยนจาก `lld` มาเป็น `mold` ตามวิธีข้างต้น mold มักจะเร็วกว่า lld เสียอีก
[**ตัวอย่าง**](https://davidlattimore.github.io/posts/2024/02/04/speeding-up-the-rust-edit-build-run-cycle.html)
ทว่า mold ยังค่อนข้างใหม่มาก และอาจยังทำงานได้ไม่สมบูรณ์ในบางกรณี

[mold]: https://github.com/rui314/mold

ตัวเลือกสุดท้ายคือ [wild] ซึ่งปัจจุบันใช้ได้เฉพาะบน Linux เท่านั้น แม้ว่าอาจจะเร็วกว่า mold เสียด้วยซ้ำ แต่ความเสถียรและความสมบูรณ์ยังน้อยกว่า

[wild]: https://github.com/davidlattimore/wild

สำหรับบน macOS ไม่จำเป็นต้องหา linker ทางเลือกมาใช้ เพราะ linker ของระบบมีความเร็วสูงอยู่แล้ว

การเปลี่ยนไปใช้ linker อื่นนั้นแตกต่างจากตัวเลือกส่วนใหญ่ในบทนี้ตรงที่ไม่มีข้อแลกเปลี่ยน (trade-off) ตราบใดที่ linker ทำงานกับโปรแกรมของคุณได้อย่างถูกต้อง (ซึ่งมักจะไม่มีปัญหา เว้นแต่คุณจะทำอะไรที่แหวกแนวเป็นพิเศษ) การใช้ linker ทางเลือกจะช่วยลดเวลาลงได้อย่างมหาศาลโดยไม่มีข้อเสียใดๆ เลย

### ปิดการสร้างข้อมูลดีบัก

แม้ว่าบิลด์แบบ release จะให้ประสิทธิภาพการทำงานดีที่สุด แต่นักพัฒนาส่วนใหญ่ก็มักใช้บิลด์แบบ dev ระหว่างเขียนโค้ดเพราะคอมไพล์ได้เร็วกว่า หากคุณใช้บิลด์ dev แต่ไม่ได้ใช้ debugger บ่อยนัก ลองพิจารณาปิดการสร้างข้อมูลดีบัก (debug info) ดู ซึ่งจะช่วยลดเวลาการบิลด์ dev ได้อย่างเห็นได้ชัด ถึง 20–40% เลยทีเดียว
[**ตัวอย่าง**](https://kobzol.github.io/rust/rustc/2025/05/20/disable-debuginfo-to-improve-rust-compile-times.html)

หากต้องการปิดการสร้างข้อมูลดีบัก ให้เพิ่มการตั้งค่านี้ลงในไฟล์ `Cargo.toml`:
```toml
[profile.dev]
debug = false
```
โปรดทราบว่าการทำเช่นนี้จะส่งผลให้ backtrace ไม่มีข้อมูลหมายเลขบรรทัด หากคุณยังต้องการให้แสดงหมายเลขบรรทัดอยู่ แต่ไม่จำเป็นต้องใช้ข้อมูลแบบละเอียดสำหรับ debugger คุณสามารถเปลี่ยนไปใช้ `debug = "line-tables-only"` แทน ซึ่งยังคงช่วยประหยัดเวลาคอมไพล์ได้เกือบเท่าเดิม

### ฟรอนต์เอนด์แบบขนานเชิงทดลอง

หากคุณใช้ Rust เวอร์ชัน nightly คุณสามารถเปิดใช้งาน [parallel front-end][parallel front-end] ซึ่งเป็นฟีเจอร์เชิงทดลองได้ ตัวเลือกนี้อาจช่วยลดเวลาในการคอมไพล์ลง โดยแลกกับการใช้หน่วยความจำระหว่างคอมไพล์ที่สูงขึ้น แต่จะไม่ส่งผลกระทบต่อคุณภาพของโค้ดที่สร้างขึ้นเลย

[parallel front-end]: https://blog.rust-lang.org/2023/11/09/parallel-rustc.html

สามารถเปิดใช้งานได้โดยเพิ่มแฟล็ก `-Zthreads=N` เข้าไปใน RUSTFLAGS ตัวอย่างเช่น:
```bash
RUSTFLAGS="-Zthreads=8" cargo build --release
```

หรือเปิดใช้งานผ่านไฟล์ [`config.toml`] (สำหรับโปรเจกต์เดียวหรือหลายโปรเจกต์) โดยเพิ่มการตั้งค่าดังนี้:
```toml
[build]
rustflags = ["-Z", "threads=8"]
```
[`config.toml`]: https://doc.rust-lang.org/cargo/reference/config.html

คุณสามารถกำหนดตัวเลขเป็นค่าอื่นที่ไม่ใช่ `8` ได้ แต่จากการทดสอบ ค่านี้มักจะให้ผลลัพธ์ที่ดีที่สุด

ในกรณีที่เหมาะสมที่สุด parallel front-end เชิงทดลองนี้สามารถลดเวลาคอมไพล์ได้สูงสุดถึง 50% ทว่าผลลัพธ์อาจแตกต่างกันไปอย่างมาก ขึ้นอยู่กับลักษณะโครงสร้างของโค้ดและการตั้งค่าการบิลด์ และในบางโปรแกรมก็อาจไม่เห็นผลเรื่องความเร็วเลย

### แบ็กเอนด์โค้ดเจน Cranelift

หากคุณใช้ Rust เวอร์ชัน nightly คุณสามารถเปิดใช้งานแบ็กเอนด์สร้างโค้ด Cranelift บน [บางแพลตฟอร์ม][some platforms] ได้ ตัวเลือกนี้ช่วยลดเวลาในการคอมไพล์ลงได้มาก โดยแลกกับคุณภาพและประสิทธิภาพของโค้ดผลลัพธ์ที่ลดลง ด้วยเหตุนี้จึงแนะนำให้ใช้กับบิลด์แบบ dev มากกว่าบิลด์แบบ release

ขั้นตอนแรก ให้ติดตั้งแบ็กเอนด์ผ่านคำสั่ง `rustup`:
```bash
rustup component add rustc-codegen-cranelift-preview --toolchain nightly
```

หากต้องการเลือกใช้ Cranelift ผ่านคอมมานด์ไลน์ ให้ระบุแฟล็ก `-Zcodegen-backend=cranelift` ตัวอย่างเช่น:
```bash
RUSTFLAGS="-Zcodegen-backend=cranelift" cargo +nightly build
```

หรือหากต้องการกำหนดผ่านไฟล์ [`config.toml`] (สำหรับโปรเจกต์เดียวหรือหลายโปรเจกต์) ให้เพิ่มการตั้งค่าดังนี้:
```toml
[unstable]
codegen-backend = true

[profile.dev]
codegen-backend = "cranelift"
```
[`config.toml`]: https://doc.rust-lang.org/cargo/reference/config.html

ศึกษารายละเอียดเพิ่มเติมได้ที่ [เอกสาร Cranelift]

[some platforms]: https://github.com/rust-lang/rustc_codegen_cranelift#platform-support
[เอกสาร Cranelift]: https://github.com/rust-lang/rustc_codegen_cranelift

## โปรไฟล์แบบกำหนดเอง

นอกจากโปรไฟล์มาตรฐานอย่าง `dev` และ `release` แล้ว Cargo ยังรองรับ [โปรไฟล์แบบกำหนดเอง] อีกด้วย ตัวอย่างเช่น คุณอาจสร้างโปรไฟล์ลูกผสมที่อยู่กึ่งกลางระหว่าง `dev` กับ `release` หากพบว่าความเร็วตอนรันของบิลด์ dev ยังไม่ทันใจ แต่เวลาในการคอมไพล์ของบิลด์ release ก็ช้าเกินไปสำหรับลูปการพัฒนาประจำวัน

[โปรไฟล์แบบกำหนดเอง]: https://doc.rust-lang.org/cargo/reference/profiles.html#custom-profiles

## สรุป

เมื่อเป็นเรื่องของการตั้งค่าการบิลด์ มีตัวเลือกมากมายให้คุณตัดสินใจ ประเด็นต่อไปนี้ได้สรุปข้อมูลข้างต้นออกมาเป็นแนวทางปฏิบัติ:

- หากต้องการเพิ่มความเร็วตอนรันให้ถึงขีดสุด ให้พิจารณาใช้ตัวเลือกต่อไปนี้ร่วมกัน:
  `codegen-units = 1`, `lto = "fat"`, ตัวจัดสรรหน่วยความจำทางเลือก และ `panic =
  "abort"`
- หากต้องการลดขนาดไฟล์ไบนารีให้เล็กที่สุด ให้พิจารณา: `opt-level = "z"`,
  `codegen-units = 1`, `lto = "fat"`, `panic = "abort"` และ `strip =
  "symbols"`
- ไม่ว่าจะเน้นความเร็วหรือขนาดไบนารี ให้พิจารณาใช้ `-C target-cpu=native` หากไม่จำเป็นต้องแจกจ่ายโปรแกรมข้ามสถาปัตยกรรม CPU ที่หลากหลาย และพิจารณา `cargo-pgo` หากเข้ากันได้กับกระบวนการเผยแพร่ของคุณ
- ควรเลือกใช้ linker ที่เร็วกว่าเสมอหากอยู่บนแพลตฟอร์มที่รองรับ เพราะไม่มีข้อเสียใดๆ จากการทำเช่นนั้น
- หากต้องการตัวช่วยทีละขั้นตอนในการตัดสินใจเลือกค่าคอนฟิกเหล่านี้ สามารถใช้เครื่องมืออย่าง `cargo-wizard` ได้
- ให้ทำเบนช์มาร์กวัดผลการเปลี่ยนแปลงทีละอย่างเสมอ เพื่อให้แน่ใจว่าส่งผลตามที่คาดหวังจริง

สุดท้ายนี้ [issue นี้] ได้ติดตามวิวัฒนาการในการปรับแต่ง build configuration ของตัวคอมไพเลอร์ Rust เอง แม้ว่าระบบบิลด์ของคอมไพเลอร์ Rust จะแปลกและซับซ้อนกว่าโปรแกรม Rust ทั่วไปอยู่มาก แต่ issue ดังกล่าวก็เป็นกรณีศึกษาที่ดีในการแสดงให้เห็นว่าเราสามารถนำตัวเลือกการตั้งค่าบิลด์ต่างๆ ไปประยุกต์ใช้กับโปรเจกต์ขนาดใหญ่ได้อย่างไร

[issue นี้]: https://github.com/rust-lang/rust/issues/103595
